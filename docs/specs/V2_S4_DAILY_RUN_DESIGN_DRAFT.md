## 3. S4の分割と順序（D-1）

| 単位 | 中身 | 外部とのつながり | 本書での扱い |
|---|---|---|---|
| **S4-A 朝の1回の実行** | 追いつき（前回より後の確定セッションを古い順に消費し、1日ずつ保存）、対象日の決定（注入した時刻から）、最新セッションの評価、プレビュー文面と実行報告（§5） | なし。保存先は注入（試験はC-3のローカル保存先と偽物） | **限定依頼を作る** |
| S4-B 通知の記録と送信権 | outbox（意図・結果）、送信権（新規作成だけ）、UNKNOWNは自動で再送しない、resend_request_idによる手動の再送（上位§5.2・§5.3第3版）、偽の送信アダプタ | なし。ローカルのファイルと偽物 | 方針だけ（§6.1） |
| S4-C gitの保存先アダプタ | 案A・案Bに共通の比較交換（早送りだけのpush）、成否不明の判定（上位§3.8）、再試行の上限（U-12）。C-3と同じ read／publish／reconcile の形 | 試験はローカルのbareリポジトリだけ（ネットなし） | 方針だけ（§6.2） |
| S4-D 入力アダプタ | 市場データの取得と版の固定、セッション（カレンダー）と確定の印、台帳（F&G観測）の読込みとSHAの記録 | 本番では取得先へ接続。試験は固定の入力 | 方針だけ（§6.3） |
| S4-E 本番接続 | 非公開リポジトリの作成（ユーザー）、workflow、秘密の登録、通知アダプタ（Discord）、試運転、本番切替・停止解除 | あり | 各段階で**別の承認**（§6.4） |

**順序の推奨：A → B → C → D → E。**

- Aを最初にする理由は3つある。
  - Aはつながりを持たない純粋に近い組立てで、既存の受領済みパッケージだけで作れる（§8で確かめた）。
  - B〜Eはどれも「Aが返す実行報告」を入力にする。
  - 工程0の不具合（最新価格の欠損を「条件未達」として正常終了した）と同じ種類の誤りを防ぐ規則（最新セッションが未確定なら判定を出さない）は、Aの中で決まる。
- Bは、通知を本当に送る前に必要である。
- CとDはU-01・U-11（保存先・台帳の場所）に依存する。§4の推奨が採用されれば、どちらもオフラインで作れる。
- Eだけが外部を変える。ユーザーの作業（リポジトリの作成）、秘密の登録、workflowの変更、送信は、それぞれ直前に別の承認を取る。

代わりの案：

- E（本番の判断と作成）を先に進める案：外部の作業が先に固まる。ただし、つなぐ中身（A・B）が無いので試運転ができず、得るものが少ない。
- Dを先にする案：取得先の版の固定（U-07）を早く決められる。ただし取得先の選定は、別の判断（データ取得の契約・課金なし）に触れ得るので、Aの後にする。

## 4. S4の前に決める判断（D-2）

S1設計§6の求めに従い、4つをまとめて示す。**ここで採るのは方針だけ**である。リポジトリの作成・秘密の登録・workflowの変更は、S4-Eの各段階で、その直前に別に承認を取る。

| ID | 判断 | 推奨 | 理由・条件 |
|---|---|---|---|
| U-01 | 保存先 | **案B：別の非公開リポジトリ**（上位§3.2、Rockyさんの2026-10-28の推奨と同じ） | 比較交換（早送りだけのpush）が新しい課金なしで手に入る。日々の観測・運用記録を公開しない |
| U-11 | 台帳（F&G観測）の置き場所 | **同じ非公開リポジトリの別の参照（例：ledger）**。ユーザーが書き、ランナーはコミットSHAを決めて読み、そのSHAを実行報告に残す | 状態の参照（ランナーが書く）と台帳の参照（ユーザーが書く）が別なので、互いの比較交換が衝突しない。ユーザーの記録の手間（スマートフォンからファイルを編集する等）はS4-Dで具体化する |
| U-13 | 実行場所と資格情報 | **非公開リポジトリのActionsで動かす。コードは公開リポジトリから固定のコミットSHAで取得する。書込みにはそのリポジトリ自身のGITHUB_TOKEN（contents: write）だけを使う**。通知先のURLは非公開リポジトリの秘密に置く | 別のリポジトリへ書くための長期トークンやGitHub Appの登録が要らない。コードの版を変えるときは、非公開リポジトリでSHAを書き換えるコミットが要る（版の採用が記録に残る）。公開リポジトリのworkflowは停止のまま |
| 送信権・再送 | 通知の契約 | **上位§5.2・§5.3（第3版）をそのまま採る**。意図は新規作成だけで、自分のclaim_idが保存された実行だけが送る。UNKNOWNは自動で再送しない。再送はユーザーがresend_request_idを指定した依頼だけで、SENTの再送依頼は受け付けない | 二重送信を構造的に防ぐ。同じ内容でも成功扱いにしない（状態の遷移とは違う） |

U-13の推奨は上位§8で「実装の承認時に提案する」とされていたものの具体案で、今回が初出である。残る条件・リスクは次のとおり。

- 非公開リポジトリのActionsは利用時間の無料枠の対象になる。毎朝の数分の実行は収まる見込みだが、現行の上限は作成時に確かめる（未確認）。課金が要るなら、その時点で止めて知らせる。
- GitHub Freeの個人アカウントでは、非公開リポジトリにブランチ保護を設定できない場合がある（作成時に確かめる。未確認）。設定できない場合、強制pushの禁止は次の2つに頼ることになる。
  - ランナーのコードが強制pushを使わないこと（S4-Cで静的な試験を置く）。
  - 状態のhash鎖の検査。
  ただし、hash鎖の検査は改ざんを見つけるが、**正しい古い先頭への巻戻しは見つけられない**。対策として、毎朝の通知に先頭の通番とhashの短縮形を1行添え、ユーザーの目に触れるようにする案をS4-Bで具体化する。
- GITHUB_TOKENは実行中だけ有効で、範囲はそのリポジトリに限られる。漏れた場合の影響は状態と台帳の改ざん・削除で、上の巻戻しと同じ対策で気づく。

## 5. S4-Aの設計（D-3）

### 5.1 入口と範囲

新しいパッケージ`v2_daily_run`（4ファイル以内）に、入口を1つ置く。

    run_morning(store, now, series, sessions, raw_observations) -> RunReport

| 引数 | 契約 |
|---|---|
| store | `read()`・`publish(publication)`・`reconcile(publication)`を持つ保存先。試験ではC-3の`HistoryFileStore`と偽物。S4-Cのgitアダプタも同じ形にする。ランナーは`initialize`・解錠・移行・採用を呼ばない |
| now | 時刻つきの`datetime`（tzinfoあり）。ランナーは時計を読まない。本番では入口のスクリプト（S4-E）が渡す |
| series・sessions・raw_observations | 既存のコア・C-2と同じ値。ランナーは変えずに渡すだけ。台帳の完全性はランナーでは証明しない（S1設計§4と同じ） |

S4-Aに含めないもの：時計・環境変数・ネット・ファイルの直接の操作、通知・outbox・送信、保存先の初期化・解錠・移行・採用、再試行、市場データ・台帳の取得、入口のスクリプト・CLI、workflow。

### 5.2 対象日の決定

- 対象D＝`close_at <= now`である最後のセッション（同じ時刻はそのセッションに含める）。無ければ`run_no_closed_session`。
- **開始位置**は`read_effective(history).processing_after`とする。これは現在のまとまり（セグメント）の`as_of_d`で、まだAPPLYが無ければGENESISの`start_after`かRESTART_UNKNOWNの`resume_after`である（上位§2.8、第2版でN-01を反映）。`latest_apply_d`は再初期化の前のまとまりのAPPLYも数えるので使わない。使うと、再初期化（S3-B-3）の後の朝がすべて`target_not_after_boundary`で止まり、自分では抜け出せない。
- 開始位置より前に対象Dがある場合（時刻が戻った、セッションの一覧が変わった）は`STOPPED`（`run_target_before_head`）とする。何も書かない（試行のT-2）。
- 開始位置より後で、対象D以前にあるセッションを古い順に調べる。**未確定（confirmed=false）のセッションに当たったら、そこで止める**。それより前の確定セッションの消費は保存したまま、結果を`STALE`（判定を出さない、終了1）にする。後ろに確定セッションがあっても飛ばして進まない。
  - 工程0の不具合は、最新価格の欠損を「条件未達」として正常終了したものだった。この規則はそれと同じ種類の誤りを防ぐ。古い日へ落とした判定や、前日値による補完もしない（CLAUDE.md §6）。

### 5.3 追いつき

確定セッションSごとに、次を行う。

1. `prepare_history_day(history, S, …)`を呼ぶ。
2. 結果が`PREPARED`なら、`publish_day(history, S, …)`で公開値を作り、`store.publish`で保存する。保存の結果のHistoryを次のSの入力にする。
3. 結果が`NO_COMMIT`か`ALREADY_APPLIED`なら、何も保存しない。

- 1日1件の保存にする（上位§3.4の手順4と同じ）。途中で止まっても、それまでの日は保存済みで、次の実行が続きから進む。
- decisionが無い日は保存しない。次に消費する日の遷移で、コアが欠測（gap、skipped_sessions）として扱う。
- 観測窓の外のdecision、台帳の食い違い（ledger_mismatch）、市場データの欠け等のコアの誤りは、そのSで`STOPPED`にする。後のSは処理しない。
- 対象Dでdecisionがまだ無ければ`NO_COMMIT`で、文面は「F&G観測待ち」の分岐表になる。対象Dのdecisionが朝の実行より前に記録されていれば、対象Dも消費し、文面はその結果になる。

### 5.4 保存先の誤りと成否不明

| 保存先の結果 | ランナーの動き |
|---|---|
| 成功 | 返ったHistoryで続ける |
| `store_commit_uncertain` | `store.reconcile(同じ公開値)`を1回だけ呼ぶ。`PUBLISHED`か`PUBLISHED_THEN_EXTENDED`なら`store.read()`で読み直し、**有効な先頭から追いつきをやり直す**（同じ実行の中では高々1回。2回目の成否不明は`STOPPED`（`run_publish_uncertain`））。`NOT_PUBLISHED`は`STOPPED`（`run_publish_not_published`）、`CONFLICT`は`STOPPED`（`run_publish_conflict`）。`reconcile`自体の誤りも`STOPPED` |
| それ以外のCoreError（store_busy、store_uninitialized、store_read_only、store_layout_unsupported、store_artifact_present、publication_stale等） | `STOPPED`。そのcodeを報告する。自動で解錠・移行・再試行しない（ロックの残留は人がC-4の手順で扱う。a6340c3 §5.1） |

- S4-Aでは保存を再試行しない。止まった日は、次の実行が同じ基点から消費し直す。
- 同時に走った実行は、どちらも止まり得る（一方がstore_busy、もう一方がpublication_staleで、保存は途中の日まで）。同じDの記録が二重になることはなく、次の実行で追いつく。本番では上位§3.6の層1（Actionsのconcurrency）で実行を1つにする（第2版でN-02を反映）。
- 再試行の回数（U-12）は、通信の失敗があるS4-Cで決める。

### 5.5 実行報告と文面

`RunReport`は不変の値で、次を持つ。

- outcome：`DONE`／`STALE`／`STOPPED`。
- 終了コード：DONEは0、ほかは1。
- 対象D。
- 消費した日の一覧：各日のD、状態、gap、skipped_sessions。
- 対象Dの状態。
- 文面。
- 止まった理由：code・field・rule。
- 最後に読んだ、または保存したHistoryのdigest。

文面の規則は次のとおり。

- `DONE`：消費した各日について、欠測があれば、それを示す1行を置く（試行のT-1）。そのあとに、対象Dの`render_message`（既存のコア）の全文を置く。
  - 欠測の行は、試行で見つけた問題への対策である。欠測は消費した日の遷移に記録されるが、対象Dの文面には出ない。このため、朝の文面だけを読む人は、前のセッションの記録が欠けたことに気づけない。
- `STALE`・`STOPPED`：判定・分岐表・b\*を出さない（U-08の推奨）。次を書く。
  - 「条件未達ではない」こと。
  - 止まった理由のcode。
  - それまでに保存した日。
  - 前日値で補っていないこと。
- 文面と報告に、パス・例外の本文・URL・秘密を入れない。

### 5.6 例外の扱い

- 引数の誤り（nowに時刻帯が無い、sessionsの型、storeに3つのメソッドが無い）は、保存先を読む前に`RunError`（CoreErrorの子）で止める。
- 保存先を読んだ後に起きたCoreErrorは、すべて`RunReport`の`STOPPED`にする。
  - 誤りは例外処理の中で値にして、外で返す（C-4の規則C4-19と同じ考え方）。OSの例外を`__context__`に残さない。
- CoreError以外の例外（プログラムの誤り）は、握りつぶさずにそのまま上へ出す。

### 5.7 変えないもの

既存のパッケージ（v2_core〜v2_history_maintain）、既存の試験・ヘルパー、範囲試験（test_c4_09の1行を除く）、main.py、workflow、依存は変えない。ランタイムがimportしてよいのは、標準ライブラリの`datetime`、v2_core、v2_history_ops、v2_history_publishだけとする。v2_history_local・v2_history_maintainはimportしない（保存先は注入する）。

## 6. S4-B〜S4-Eの方針（今回は依頼しない）

### 6.1 S4-B 通知の記録と送信権

- 上位§5.2・§5.3第3版の契約を、保存先から独立した値と手順として作る。
  - 鍵は「対象Dと種別」。
  - 意図は新規作成だけ。
  - 結果は送信権を持つ実行だけが書く。
  - 意図だけ残っていればUNKNOWN。
  - 再送はresend_request_idによる。
- 最初はローカルのファイル（O_EXCLの新規作成）と偽の送信アダプタで試す。
- 送信の失敗は、送信を始める前に失敗したことが確かな場合だけNOT_SENT、それ以外はUNKNOWNにする（U-04の推奨）。同じ実行の中での自動再送も、最初は作らない。
- STALE・STOPPEDの日にも通知の意図を作り、「判定なし」を知らせる（無通知にしない）。
- §4の巻戻しの対策（先頭の通番・hashの短縮形を文面に添える）をここで決める。

### 6.2 S4-C gitの保存先アダプタ

- C-3と同じ`read／publish／reconcile`の形にする。
- 状態の参照を早送りだけで更新し、拒否されたら読み直す。
- 成否不明のときは、上位§3.8の順で判定する（自分のコミットのSHAへの到達 → 有効な履歴の同じD）。
- 再試行は少数回（U-12、例：最大4回）。
- 強制pushを使わないことを静的に試験する。
- 試験は、一時ディレクトリのbareリポジトリだけで行い、ネットに出ない。gitコマンドの版を記録する。

### 6.3 S4-D 入力アダプタ

- 市場データの取得先と版の固定は、価格改訂（U-07）の扱いと一緒に決める。
- セッションの確定の印をどこから得るかも決める。
- 台帳は、非公開リポジトリのledger参照から、コミットSHAを決めて読む。
- ユーザーの記録の手順（入力の形、スマートフォンからの記録）を具体化する。
- 取得先の新しい契約・課金はしない。

### 6.4 S4-E 本番接続（各段階で別の承認）

段階と、それぞれの承認は次のとおり。

1. ユーザーによる非公開リポジトリの作成（このセッションからは作れない）。
2. 非公開リポジトリへのworkflowの追加（同じ朝の実行を1つにするconcurrencyのグループを含む。§5.4）と、通知先の秘密の登録（ユーザー）。
3. 送信なしの試運転（偽の送信アダプタ、または送信を無効にした設定）。
4. 実送信の試験。
5. 本番の定時実行の有効化と、main 31144d9の停止の扱い。

公開リポジトリのmain・workflow・既存の通知先は、承認なしに変えない。
