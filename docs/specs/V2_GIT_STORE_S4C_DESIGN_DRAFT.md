## 0. 要約

- S4-Bは6cab050で受領済みである（受領記録983ced8、提案の採否9b4d786）。採用済みのS4設計（7542a18、D-1）の順序では、次は**S4-C gitの保存先**である。

- 試行（§10）で、S4-A・S4-Bを無変更のまま、gitの保存先の上で朝の処理が動くことを確かめた。
  - 別のクローンからの再実行も、送信は1通だった。
  - 同時に2〜4実行を各10回走らせ、毎回「判定あり」と「判定なし」が1通ずつ届いた（S4-BのT-3と同じ）。二重の判定は0回だった。

  - pushの拒否は既存のコード`publication_stale`にする。そうすれば、S4-Bの「同時の実行」の注記がそのまま付く（T-3）。
  - outboxの読込みは例外を出さない。リモートに届かなければDAMAGEDと読み、送らない（T-2）。
  - 他のパッケージの非公開の名前（`_base`・`_of`）を使わずに組める（T-5）。
- S4-Bの範囲試験のENDを6cab050に固定する（1行、§9.1）。S4-B実装レビューの未対応の提案P-01〜P-04は、S4-Cでは直さず、行き先を§9.2に決めた。R2-P01は、S4-Eの入口の条件として引き継ぐ（§9.3）。

## 3. 参照の配置（D-2）

採用済みD-2（U-01 案B：別の非公開リポジトリ、U-11：同じリポジトリの別の参照）を、次の形にする。

| 参照（例） | 中身 | 書く者 |
|---|---|---|
| `refs/heads/v2-state` | `history.json`の1ファイルだけ | ランナー（`GitHistoryStore`） |
| `refs/heads/v2-outbox` | 初期化の印のファイル1つと、意図・結果のファイル（S4-Bと同じ名前・同じバイト） | ランナー（`GitOutbox`） |
| `refs/heads/v2-ledger` | 台帳（S4-Dで決める） | ユーザー |

- 履歴とoutboxを別の参照にする。1つにすると、通知の記録のpushが履歴の比較交換を失敗させ、その逆も起きる（試行の前の検討。どちらも理由の無い`publication_stale`になる）。
- 参照の名前は呼び出し側が渡す。S4-Cでは名前の形だけを検査する（英小文字・数字・`-`、1〜40文字、`-`で始まらない）。実際の名前はS4-Eで決める。
- どの参照も、親が1つの早送りのコミットだけで進む。各コミットは、`v2-state`では`history.json`だけを変え、`v2-outbox`ではファイルを1つ足すだけである（S4C-15）。

## 4. gitの層`Git`（D-3）

`Git(workdir, remote="origin", timeout=120)`。gitの子プロセスを起動するのは、パッケージの中でこのクラスだけである。

1. **作業場所**：`workdir`は呼び出し側が用意したgitのリポジトリ（S4-EではActionsのチェックアウト、試験では`git init`と`remote add`をしたもの）。コミットは配管コマンド（`hash-object`、`mktree`、`commit-tree`）で作る。作業ツリー・インデックス・HEAD・`refs/heads/*`を変えない。取得は`+refs/heads/<参照>:refs/v2remote/<参照>`の専用の名前空間へだけ行う。
2. **コマンドの形**：引数の配列だけで起動する（`shell`を使わない）。毎回`-c core.autocrlf=false -c commit.gpgsign=false`を付ける。環境は親の環境の写しから`GIT_`で始まる変数を除き、`GIT_TERMINAL_PROMPT=0`、`LC_ALL=C`、`GIT_CONFIG_NOSYSTEM=1`と、作者・コミッターの固定の名前・メールを足す。コミットの日時は注入した時計から渡す（パッケージは時計を読まない）。
3. **push**：`git push --porcelain <remote> <sha>:refs/heads/<参照>`だけ。`--force`、`--force-with-lease`、`+`つきの参照指定、`--mirror`、`--delete`、`--quiet`を使わない（T-1）。結果は出力の参照の行の記号で3つに分ける。

   | 結果 | 条件 |
   |---|---|
   | OK | 記号が`*`・空白・`=`で、終了コードが0 |
   | REJECTED | 記号が`!`（早送りでない、既にある参照の作成、リモートの拒否） |
   | UNCERTAIN | それ以外すべて（時間切れ、参照の行が無い、記号がOKなのに終了コードが0でない） |

4. **取得**：取得が成功すれば先頭のSHAを返す。失敗した場合は`ls-remote`で確かめ、参照が無いことが確かなときだけ「無い」（None）とし、ほかは`GitError`にする。取得の失敗を「無い」と読まない（欠陥注入5）。
5. **出力を外へ出さない**：gitの標準出力・標準エラーには、リモートのURLや資格情報が含まれ得る。例外の引数・報告・文面・ファイル・コミットのメッセージに入れない。`GitError`の引数は固定の語だけにする。
6. **時間切れ**：既定は120秒。時間切れのpushはUNCERTAIN、ほかのコマンドは失敗とする。再試行はしない（§7）。

## 5. 履歴の保存先`GitHistoryStore`（D-4）

`GitHistoryStore(git, ref, clock)`。S4-Aのランナーが使う3つのメソッドと、初期化を持つ。

| メソッド | 振る舞い |
|---|---|
| `read()` | 取得して`history.json`を`read_history_bytes`で読む。参照が無ければ`store_uninitialized` |
| `publish(pub)` | 取得→今のバイトを検査→`check_publication`→1コミット→push。結果はC-3と同じ`HistoryStoreResult` |
| `reconcile(pub)` | 取得し直したバイトで`reconcile_publication`（C-2）を返す |
| `initialize(pub)` | 参照が無いときだけ、GENESISの公開で最初のコミットを作ってpushする。あれば`already_initialized` |

誤りは既存の`LocalStoreError`のコードだけで表す。新しいコードは作らない。

| 場面 | コード | S4-Aの結果 |
|---|---|---|
| 取得・読込みの失敗、`GitError` | `store_io_error` | STOPPED |
| 参照はあるが`history.json`が無い | `store_layout_unsupported` | STOPPED |
| pushがREJECTED（読んだ後にリモートが進んだ） | **`publication_stale`**（T-3） | STOPPED。判定なしの文面に「同時の実行」の注記が付く |
| pushがUNCERTAIN | `store_commit_uncertain` | ランナーが`reconcile`を1回だけ呼ぶ（S4-A） |
| 公開の検査の失敗 | C-2のまま（`publication_invalid`等） | STOPPED |

成否不明の判定は、**内容だけ**で行う（D-4の要点）。上位§3.8は「自分のコミットのSHAへの到達→有効な履歴の同じD」の順を書いているが、次の理由で内容の判定に置き換える。

- Actionsの実行は毎回新しい環境で、前の実行が作ったコミットのSHAを覚えておけない。同じ実行の中でも、SHAを覚えるには、C-2の非公開の値の作り方（`Reconciliation._of`）を使う必要がある（T-5）。
- `reconcile_publication`は、リモートの`history.json`がこちらの候補そのものか（PUBLISHED）、候補を物理的な先頭に含むか（PUBLISHED_THEN_EXTENDED）を、候補のダイジェストで判定する。自分のコミットに到達できるなら、リモートは候補か、その延長である（早送りだけで進み、追記の公開は先頭を変えないため）。逆に、内容が一致しても到達できない場合は、同じ候補を別の実行が先に保存した場合だけで、どちらでも履歴は同じである。
- 保守の操作で履歴が置き換えられた後は、到達できても内容は一致しない。この場合はCONFLICTになり、STOPPEDで止まる（安全側）。

## 6. outbox`GitOutbox`（D-5）

`GitOutbox(git, ref, parent, clock, *, _ops=None)`。S4-Bの`LocalOutbox`の子クラスにする。`_ops`は試験用で、基底へそのまま渡す（写しへの書込みの失敗を作るため）。

- S4-Bの`morning_job`・`resend`は、`isinstance(outbox, LocalOutbox)`を検査する。子クラスにすれば、受領済みのv2_notifyを変えずに使える。別の型にするなら、v2_notifyを変える必要がある（採らない）。
- 上書きするのは公開のメソッド（`load`、`resend_ids`、`claim`、`record`）だけである。`status`と`outbox_status`は、基底の`load`を通して動く。基底の非公開の名前（`_base`、`_create`、`_read`、`_ops`）を使わない（T-5）。

**写しのディレクトリ**：`parent`（既存の絶対パスのディレクトリ）の中に、`GitOutbox`が自分で`tempfile.mkdtemp`で作る。基底の`LocalOutbox`のrootはこの写しで、モードは`file_sync_only`に固定する。写しは毎回リモートから作り直す一時のものであり、正本はリモートのコミットだからである（strictのディレクトリ同期は意味を持たない）。作り直しで消すのは、この写しの中のファイルだけである。

**読込み**（`load`）：

1. 取得して、写しをリモートの木と同じにする。
2. 取得・作り直しに失敗したら、例外を出さずに`OutboxEntry(kind, d, resend_request_id, DAMAGED)`と`None`を返す（T-2）。S4-Bの`morning_job`は状態の確認を例外処理なしで呼ぶため、ここで例外を出すと、朝の処理全体が例外で終わる。DAMAGEDなら、どの種類も送らない。
3. 成功したら基底の`load`の結果を返す。

`resend_ids`は取得の失敗を`NotifyError`（`outbox_io_error`）にする。S4-Bの`resend`は、これをCLAIM_FAILED（送らない）として返す。再送の可否を確かめる間に、`load`・`status`ごとに取得し直すので、取得の回数は再送の数に比例する（再送は手動でまれなので、まとめる工夫はしない）。

**意図・結果の作成**（`claim`、`record`）：最大4回、次を繰り返す。

1. 取得して写しを作り直す。
2. 基底の`claim`／`record`で、写しにファイルを新規作成する。既にあればNone／Falseを返して終わる（このときは送信権を持たない）。
3. 写しに増えたファイルがちょうど1つであることを確かめ、その名前とバイトで、取得した先頭を親とするコミットを作り、pushする。
4. OKなら、基底の値（claim_id／True）を返す。
5. REJECTED・UNCERTAIN・`GitError`なら、取得し直して、リモートの同じ名前を見る。
   - 自分と同じバイトがあれば、自分の作成とする（UNCERTAINのpushが実際に届いた場合）。
   - 違うバイトがあれば、他の実行が先に作ったので、None／Falseを返す。
   - 無ければ、別の鍵のファイルで参照が進んだだけなので、1へ戻る。
6. 4回とも決まらなければ`NotifyError`（`outbox_io_error`）。S4-Bの`morning_job`はCLAIM_FAILED（送らない）、結果ならRESULT_NOT_RECORDED（意図はリモートに残り、次の実行は送らない）にする。

途中で取得し直しに失敗した場合も`NotifyError`にする。UNCERTAINのpushが実は届いていて取得し直しに失敗したときは、意図はリモートにあるのに送らない。次の実行はUNKNOWNと読んで送らないので、二重には送らない。手動の再送で回復する（無通知の側に倒れる。§11）。

**初期化**：`initialize()`で、印のファイル1つを持つ最初のコミットを作ってpushする。参照が無いoutboxは、空のoutboxと読まずに、読込みはDAMAGED、作成は`NotifyError`とする。参照の削除・取り違えを「送ってよい」と読まないためである（欠陥注入16）。

**途中まで書いた写し**：基底の作成が途中で失敗した写しのファイルは、pushされない（pushは作成が成功した後だけ）。次の作り直しで消える。S4-Bの空・途中までの意図（DAMAGED）は、gitの保存先ではリモートに残らない。

## 7. 再試行と時間（U-12、D-6）

S4設計§6.2は「再試行は少数回（例：最大4回）」とした。S4-Cでは次のとおりにする。

| 場面 | 再試行 |
|---|---|
| 履歴のpush | **しない**。拒否はSTOPPED（`publication_stale`）、成否不明はS4-Aのreconcile 1回 |
| 取得 | **しない**。失敗は履歴ならSTOPPED、outboxならDAMAGED（送らない） |
| outboxの作成 | 別の鍵のファイルで参照が進んだときだけ、**最大4回**（待たずに取得し直す） |
| 時間を置いた再試行 | **作らない**。パッケージは時計・sleepを使わない |

通信の一時的な失敗で朝の通知が出ない日がありうる。これは「来なければ止まっている」として扱う（S4-B §5）。対策は、S4-Eで同じ朝に定時の実行を2回置くことを推奨する（例：日本時間7:00と7:30）。朝の処理は鍵で1通に限るので、1回目が送れていれば2回目は送らない（SKIPPED_CLAIMED）。時間を置いた再試行をコードに入れるより、試験が単純で、実行の記録にも残る。

## 8. 巻戻しの表示（D-7）

採用済みD-2の注意（非公開リポジトリでブランチ保護が使えない場合、正しい古い先頭への巻戻しはhash鎖で見つからない）への対策として、S4-B §9は「先頭の通番とhashの短縮形を文面に添える案をS4-Cで決める」とした。

**推奨：S4-Cでは入れない。S4-Eで、ブランチ保護（またはルールセット）が使えるかを確かめてから、もう一度決める。** 理由は次のとおり。

- 先頭の情報は、S4-Aの`RunReport`にもS4-Bの`compose`にも無い。入れるには、受領済みの2つのパッケージを変える必要がある。
- 巻戻しの影響は限られる。台帳と市場データが同じなら、次の朝の追いつきで同じ日が同じ内容で積み直され、判定は変わらない。outboxが同時に巻き戻されない限り、同じDの通知は二度送られない。両方が巻き戻された場合も、起きるのは同じDの重複の通知で、誤った判定ではない。
- 毎朝、通番とhashの短縮形を目で比べる手間に比べて、見つけられる場面が狭い。

代わりに、S4-Eの条件として次を残す。

- 非公開リポジトリで、`v2-state`・`v2-outbox`への強制pushと削除を禁じる設定ができるかを、作成時に確かめる。
- できない場合は、その事実と、巻戻しが見つからないリスクを、利用者の判断として記録する。表示を入れるなら、そのときRunReportとcomposeの小さな変更として別に設計する。

案を採らずに、S4-Cの中で表示を入れる選択肢もある（D-7の代案）。その場合はv2_daily_runとv2_notifyの変更が範囲に入り、受入と範囲試験が大きくなる。

## 9. 前の段階からの引継ぎ（D-8）

### 9.1 S4-Bの範囲試験の固定

S4-Cの最初のコミットで、tests/v2_notify/test_s4b_09_scope.pyの18行目を次のように変える（1行だけ）。同じコミットで、S4-Cの開いた範囲試験（トップレベルの`START`＝6cab050、`END = None`、`class FilesChanged`）を足す。

## 11. 残るリスクとS4-Eへの条件

- **リモートに届かない朝は無通知になる。** 履歴もoutboxも読めないため、判定なしの通知も出せない。§7の2回の定時実行と、「来なければ止まっている」の利用者向けの説明で扱う。
- **送信は済んだのに結果を記録できない**（結果のpushの失敗）：意図はリモートにあり、次の実行はUNKNOWNと読んで送らない（S4-Bと同じ）。
- **ブランチ保護が使えない場合の巻戻し**：§8。
- **資格情報**：S4-Cは扱わない。S4-Eでは、ActionsのチェックアウトがGITHUB_TOKENをリポジトリの設定に置く形を使い、URLに資格情報を書かない。gitの出力を外へ出さない規則（§4の5）は、資格情報が出力に混ざる場合への備えである。
- **保守の操作**：C-4の復元・診断・採用は、ローカルの保存先に対する操作である。gitの保存先で必要になったときは、`history.json`をローカルの保存先へ取り出して操作し、結果を公開として戻す手順を、S4-Eで書く（コードは作らない）。
