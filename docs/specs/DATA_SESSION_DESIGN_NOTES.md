どちらも提案で、変更を実装していない。単一取得の整合性、価格欠落時の扱い、当時利用可能だった値と後日改訂の区別を評価して1つを推奨する。Adj Close欠落時にCloseへ黙って代用しない。

調整価格を指標に使うこと自体が、即座に現金分配の二重計上になるわけではない。損益計算へ調整済みリターンを入れてさらに現金を足す等の混在を避ける。auto_adjust=Falseを「完全に無調整」「当時の実約定」とも呼ばない。

価格契約に残すもの：銘柄・データ源・依存版・取得引数・系列名・調整基準・通貨・対象セッション・観測時刻・保存版。固定データでの比較と実データ取得・実約定検証を分ける。

## 3. 対象セッションをデータから独立して決める

市場カレンダー、America/New_York／UTC／Asia/Tokyoの変換、実際の実行時刻を使う方式を第一候補とする。カレンダーの選択・対応市場・有効期間・データ確定待ち時間はまだ未選定。公式取引所資料と、採用候補ライブラリの該当版を照合する。

設計で必ず明確にする：
- 定期イベントが意図した取引日と、実起動時刻から求めた取引日をどう扱うか。予定時刻が証拠として得られない場合に推測で作らない。
- 通常日、休場、短縮取引、夏冬時間の切替、週末、遅延、NY日付を跨ぐ実行、手動再実行。
- 「市場が閉じた」と「上流の日足が確定・到着した」を分ける。カレンダー上終了しただけで取得データの検査を省略しない。
- 先に対象日を決め、当該範囲で取得・元価格／履歴／日付を検査する。古い共通日へ後退しない。
- 休場時の正常スキップ、早過ぎる実行、カレンダー不明／期限切れ、取得欠損の状態と終了コードを分け、毎回サマリの承認に整合させる。
- 手動の日付指定は誤った古いデータで正常運用に見えないようにする。過去日の再現と通常実行を区別し、再送の可否は実行しない。

営業日単位の行が丸ごと欠けた場合、行数と最終日だけでは検出できない。カレンダーと必要履歴の連続性検査をどの層で行うかも仕様化する。必要以上の全銘柄全履歴検査へ広げず、各指標の入力に対応させる。

## 4. 運用規則との境界

- 正常日も実行ごとに完了通知する採用事項を維持。対象日ごとの重複防止で、再実行の完了報告まで黙って消さない。
- 通知1回の試行を、必ず1回配信される保証と同一視しない。配信不明時の自動再送はしない。
- Sheets価格行の重複と完了サマリの重複を分ける。保有・原価は読まず、通知で約定状態を更新しない。
- 未起動を同一ワークフローから検知できない。確認期限（JST）は提案を1つ示してよいが未採用。観測した遅延だけで遅延上限を保証しない。新しい独立監視・有料サービスは導入しない。

- NT-01の試験URL隔離と依存固定は、設計後のSonnet限定作業にまとめる。元IR-01〜05の全面再レビューは不要。
