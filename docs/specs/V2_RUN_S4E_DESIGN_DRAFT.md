## 3. 入口`v2_run`（D-2）

### 3.1 コマンド

    python -m v2_run <command> --mode dry|live --workdir <非公開リポジトリのチェックアウト> [--code-version <40桁>] [...]

| コマンド | すること | 終了コード |
|---|---|---|
| `morning` | `load_inputs`→`guarded_store`→`morning_job`。実行の記録を書く | §3.4 |
| `status --date D` | `outbox_status`の各行を記録に書く。何も変えない | 0（読めなければ1） |
| `resend --date D --kind K --request-id ID` | 手動の再送（S4-Bの`resend`）。HALT・ERRORの再送は、同じDのmorningの意図があれば入口で断る（S4-B実装レビューP-02） | 送れたときだけ0 |
| `init --start-after D` | そのモードの履歴の参照にgenesis（`publish_genesis`）を、outboxの参照に印を、**それぞれ無いときだけ**作る（あるものは変えない。§13のT-5）。`D`は表の閉じたセッションに限る。市場データの固定と台帳には書かない | 両方が揃えば0、ほかは1 |
| `check-source` | 4記号を取得し、応答の事実（行数、時刻、同じ日付、表の日の欠け・null、2026年より前の研究データとの差、固定済みとの差）を記録に書く。何も書き込まない（§7） | 取得がすべて通れば0 |

### 3.2 1か所で1回だけ決めるもの（R2-P01）

`Setup`が、次をこの順に1回だけ決め、どのコマンドも同じものを使う。

1. `now`：時計を1回だけ読む（UTCの時刻帯つき）。`load_inputs`と`morning_job`に同じ値を渡す（違う値だと対象Dがずれる）。コミットの日時にだけ、時計の関数そのものを渡す。
2. `Git`：`--workdir`の作業場所で1つ。履歴・outbox・市場データの固定・台帳を、すべてこの1つで読み書きする（S4-Cの申し送り2）。
3. 参照の名前：モードで決まる。

   | モード | 履歴 | outbox | 市場データの固定 | 台帳 |
   |---|---|---|---|---|
   | `dry` | `v2-dry-state` | `v2-dry-outbox` | `v2-dry-market` | `v2-ledger` |
   | `live` | `v2-state` | `v2-outbox` | `v2-market` | `v2-ledger` |

   台帳だけは両方のモードで同じ（利用者が書く1つ）。ランナーが書く参照は、試運転と本番で分ける。試運転の記録が本番の送信権や固定を先取りしないためである。
4. 保存先：`GitHistoryStore(git, 履歴の参照, 時計)`。
5. outbox：`GitOutbox(git, outboxの参照, 一時ディレクトリ, 時計)`を1つ。`morning_job`・`resend`・`outbox_status`に同じものを渡す。`GitOutbox`は写しのモードが`file_sync_only`に固定なので、`durability`の選択は無い（S4-C設計§9.3）。
6. 送信先：`dry`は`DrySender`（何も外へ出さず、文面を記録に残し、`SENT`と答える）。`live`は`DiscordSender`（§4）。
7. 取得の関数：`make_fetch()`（§5）。

### 3.3 読むもの・読まないもの

- 入口だけが、時計・環境変数・HTTPを使う。受領済みのパッケージは、これまでどおりどれも使わない。
- 環境変数は2つだけ読む。`V2_DISCORD_WEBHOOK_URL`（`live`のときだけ）と`GITHUB_STEP_SUMMARY`（実行の記録の追記先）。
- 実行の記録（標準出力とActionsの要約）には、コード・日付・hash・数・秒だけを書く。パス・URL・秘密・例外の本文・gitの出力を書かない。例外は型の名前と固定のコードだけ。

### 3.4 終了コード

- `morning`：配達が`SENT`・`SKIPPED_CLAIMED`・`SKIPPED_JUDGMENT_EXISTS`なら0、ほか（`NOT_SENT`・`UNKNOWN`・`CLAIM_FAILED`・`RESULT_NOT_RECORDED`）と、入口の例外は1。
- 判定なし（HALT）が送れた朝も0にする。通知は届いているからである。0でない終了は「通知が届いていない、または届いたか分からない」を意味し、Actionsの失敗としてGitHubのメールが届く（定時のworkflowの失敗は、cronを最後に変えた利用者にメールで知らされる）。これが「来なければ止まっている」の2つ目の知らせになる。
- `JobReport.exit_code`（判定ありが送れたときだけ0）は使わない。STALEの朝に毎回失敗のメールが届くのを避けるためである。

### 3.5 `load_inputs`が例外を出す場合

`input_args_invalid`・`input_calendar_ended`は`load_inputs`から投げられる（S4-D）。入口はそれを捕まえ、`morning_job`にセッションなし（`None`）を渡す。S4-Aが引数の誤りとして止まり、S4-Bが予備の鍵（`<UTCの日付>-error`）のERRORを1通送る。記録には投げられたコードを書き、終了コードは1にする。表の終わり（`input_calendar_ended`）の14日前からは、`input_calendar_not_covered`の判定なしが毎朝届く（S4-D）ので、ここに来る前に気づける。

## 4. 送信（D-3）

- 送信先はDiscordのWebhookである。`POST <URL>?wait=true`、本文は`{"content": 文面, "allowed_mentions": {"parse": []}}`（`@everyone`等の一斉の通知を起こさない）、時間切れ20秒、再試行なし。
- URLは`https://discord.com/api/webhooks/`または`https://discordapp.com/api/webhooks/`で始まるものだけを使う。無い・形が違う場合は、送らずに`NOT_STARTED`。
- **S4-Bの答え（U-04の具体化）**：

  | 起きたこと | 答え | 理由 |
  |---|---|---|
  | 2xx | `SENT` | Discordが受け付けた |
  | 最初の部分で4xx（400・401・404・429等） | `NOT_STARTED` | Discordは投稿を作っていない |
  | 最初の部分で、名前の解決の失敗・接続の拒否 | `NOT_STARTED` | 送り始めていない |
  | 5xx、時間切れ、ほかの例外 | `UNKNOWN` | 投稿されたか分からない |
  | 2つ目以降の部分の失敗 | `UNKNOWN` | 一部は届いている |

  どの答えでも、同じ鍵は自動では送り直さない（S4-Bの送信権）。`NOT_SENT`・`UNKNOWN`は、利用者が`resend`で送り直す（§11）。
- **文字数**：Discordの上限は2000文字である。1900文字を超える文面は、行の境目で分け、各部分の先頭に「（n/N）」を付けて順に送る。試行の通常の文面は500〜800文字程度で、分かれるのは記録の欠けの行が多い朝だけである。
- **見出し**：コア（v2_core/display.py）とS4-A（v2_daily_run/run.py）の文面の見出し「【SOXL日次・ローカルプレビュー（実送信なし）】」は、実際に送る直前に「【詳細】」へ置き換える（`DiscordSender`の中だけ）。outboxに残る文面（と`text_sha256`）は置き換える前のものである。再送も同じ置き換えを通る。送信なしの試運転では置き換えない（文面のとおり、実際に送っていない）。受領済みのパッケージの文面と、その試験は変えない。

## 5. 取得（D-4）

- `make_fetch()`は、S4-Dの`fetch(symbol, start, end)`の形の関数を返す。URLは`chart_url`、`User-Agent`は固定の一般的な名前、時間切れ30秒、応答の上限8MB、状態200以外と上限超えは例外にする。例外は`load_inputs`で`input_market_fetch_failed`になり、その対象Dの判定なしが届く。
- 再試行はしない（U-12）。代わりに、同じ朝に定時の実行を2回置く（§6）。1回目が取得の失敗で判定なしを送っても、2回目で取得できれば判定ありが届く（S4-Bの規則：判定なしの後の判定ありは送れる）。
- 取得の関数に、gitの設定・秘密・環境変数を渡さない（S4-Cの申し送り2、S4-D§10.3）。

## 6. workflow（D-5）

### 6.1 ひな形

E-0では、ひな形を公開リポジトリのdocs/ops/V2_MORNING_WORKFLOW_TEMPLATE.ymlに置く（`.github/workflows/`ではないので、公開リポジトリでは動かない）。E-2で、Rockyさんの承認の後に、非公開リポジトリの`.github/workflows/v2-morning.yml`へ写す。中身の要点：

    name: v2-morning
    on:
      schedule:
        - cron: "40 22 * * 1-5"    # 日本時間 火〜土 7:40
        - cron: "40 23 * * 1-5"    # 日本時間 火〜土 8:40（同じ朝の2回目、U-12）
      workflow_dispatch:           # 手動：morning / status / resend / init / check-source
        inputs: { command, date, kind, request_id, start_after }
    permissions:
      contents: write              # この非公開リポジトリだけ（GITHUB_TOKEN）
    concurrency:
      group: v2-writer             # 書く実行は1つずつ（S4-Cの申し送り1）
      cancel-in-progress: false
    env:
      V2_MODE: dry                 # E-5でliveにするコミットが、本番の開始の記録になる
      V2_CODE_SHA: <公開リポジトリの受領版の40桁>   # 変えるコミットが、版の採用の記録になる（U-13）
    jobs:
      run:
        runs-on: ubuntu-24.04
        timeout-minutes: 30
        steps:
          - uses: actions/checkout@<40桁のSHA>    # 非公開リポジトリ。資格情報は作業場所のgitの設定に残る
            with: { path: state, persist-credentials: true }
          - uses: actions/checkout@<40桁のSHA>    # 公開リポジトリのコードを固定のSHAで
            with: { repository: Rocky009-jp/soxl-alert, ref: <V2_CODE_SHA>, path: code, persist-credentials: false }
          - working-directory: code
            env: { 入力はすべて環境変数で渡す。live のときだけ V2_DISCORD_WEBHOOK_URL: secrets.V2_DISCORD_WEBHOOK_URL }
            run: python3 -E -B -m v2_run "$CMD" --mode "$V2_MODE" --workdir ../state --code-version "$V2_CODE_SHA" ...

- **concurrency**（S4-Cの申し送り1）：定時の2回、手動の実行、再送、初期化を、すべて同じグループ`v2-writer`に入れる。`cancel-in-progress: false`なので、後の実行は前の実行の終わりを待つ（GitHubは待ちの実行を1つだけ残し、それより前の待ちを取り消す）。グループが効かない場合も、S4-Cの比較交換とS4-Dの固定の競合の規則で、同じDの判定は1通までである。
- **資格情報**（S4-Cの申し送り2）：`actions/checkout`の`persist-credentials: true`が、GITHUB_TOKENを作業場所のgitの設定に置く。`Git`は子プロセスの環境から`GIT_*`を除き、システムの設定を読まない（`GIT_CONFIG_NOSYSTEM=1`）が、作業場所の設定と利用者の設定は読むので、この形で動く見込みである。URLに資格情報を書かない。**これは実物で確かめていない**。E-3の最初の実行で、pushが通ることを確かめる（通らなければ止めて、設定の置き方を設計し直す）。
- **コードの版**：公開リポジトリを`V2_CODE_SHA`の40桁で取得する。`actions/checkout`もタグではなく40桁のSHAで固定し、E-2の時点で公式のリリースのSHAを確かめて書く。依存のインストールは無い（標準ライブラリだけ）。Pythonはランナーの`python3`（ubuntu-24.04は3.12）を使い、版を実行の記録に書く。
- **入力の受渡し**：`workflow_dispatch`の入力は、`run`の行に直接埋めず、環境変数で渡す（スクリプトの注入を避ける）。入口が形を検査する。
- **秘密**：E-2・E-3のひな形には秘密の行が無い。E-4で、`live`の実行のときだけ`V2_DISCORD_WEBHOOK_URL`を渡す行を足す。
- **ジョブの時間**：30分。通常の朝は1分前後。長い追いつき（§10）も収まる。

### 6.2 実行の時刻（S4-DレビューP-08、U-12）

- 日本時間の火〜土の7:40と8:40（UTCの月〜金22:40と23:40）を推奨する。

## 10. 時間の測定（S4-Cの申し送り3、U-06）

試行（§13、Linux、Python 3.13.18、git 2.43.0、4 vCPU）の結果：

|---|---|---|---|
| 1 | 0.02秒 | 0.11秒 | 0.11秒 |
| 751 | 1.92秒 | 11.16秒 | 3.58秒 |
| 1,501 | 3.59秒 | 21.27秒 | 7.28秒 |

- 1朝のファイルは、判定ありで2つ（意図と結果）、判定なしが前に届いた朝で4つである。1年（約250セッション）で約500〜750、3年で約2,000である。朝の処理は読込みを3〜4回するので、1年で数秒、3年で十数秒になる。本番の運用には足りる。
- **閾値**：実行の記録の`seconds.morning_job`が60秒を超えるか、`outbox_files`が1,500を超えたら、別の設計（`git cat-file --batch`で1回に読む、または年ごとの参照に分ける）を作る。今は作らない（受領済みのv2_git_storeを変えずに済む）。
- 入口の記録では、`outbox_status`ではなく1回の読込みだけを測る（`outbox_status`は1年で10秒を超えるため）。

追いつき（U-06）：

- 2026-01-02をgenesisにして、2026-08-11の朝に1回で149セッションを追いついた。`load_inputs`は0.33秒、`morning_job`は233秒だった。続く同じ朝の2回目は0.9秒（`SKIPPED_CLAIMED`）。

- 通常の朝（1セッション）の時間は、履歴の長さに比例して伸びる。試行の149日目の1日分は約3秒で、3年で十数秒と見込む。
- U-06（古さの上限を置かない）は、このままでよい。長い遅れは、Rockyさんが手動の`morning`で追いつかせる（定時の実行を待ってもよい）。

## 11. 利用者向けの手順書（D-8）

E-0で、docs/ops/V2_PRIVATE_RUN_GUIDE.md（日本語）を作る。Rockyさんが読んで操作できることを目的とし、次を含める。手順書は秘密の値・パス・個人の口座の情報を含めない。

1. 毎朝の流れ：通知が届く時刻（日本時間7:40〜9:00ごろ）、届かない朝（日・月、米国の休場日の翌朝）、届くべき朝に9:30までに来なければ止まっていると読む（Actionsの画面と失敗のメールを見る）。
2. 台帳の書き方：`v2-ledger`の`observations.csv`をGitHubのウェブ（スマートフォン可）で開き、1行足してコミットする。列、record_idの付け方、時刻は必ず`+09:00`付き、合図なしの日もdecisionを記録する、未確認は`not_checked`、古い行を消さない（S4-D§6）。
3. 通知の読み方：判定あり・判定なし・実行の誤りの違い。同じDの判定なしの後に判定ありが届いたら判定ありが有効（S4-C§7）。「【詳細】」の部分はコアの文面。
4. 手動の操作：`workflow_dispatch`で`status`・`resend`・`morning`・`check-source`を走らせる方法と、入力の書き方。
5. 再送：`NOT_SENT`・`UNKNOWN`の朝は`status`で確かめてから`resend`（新しいid）。HALT・ERRORの再送は、同じDの判定ありがあれば断られる。CLAIM_FAILEDの扱い（§9の4）。
6. DAMAGED：一時的な読めなさか、壊れたファイルかを、時間を置いた`status`で見分ける。壊れたままなら止めてClaudeに相談する（手で直さない）。
7. 止まり続ける理由コードごとの扱い：`input_market_fetch_failed`（取得先の不調、次の朝を待つ。続けば相談）、`input_market_rows_missing`・`input_calendar_data_mismatch`（取得先の欠け・表の誤り。続けば相談。固定済みの値で埋める操作はまだ無い）、`input_ledger_*`（台帳を直す）、`input_calendar_not_covered`（表の延長が要る）、`session_context_mismatch`（臨時の休場・短縮の後。保守の操作）。
8. 休場日の表：毎年12月に、取引所（ICE）の発表を読んで翌々年の分を足し、照合の出典と日付を残す。臨時の休場・短縮取引は、発表されたらその日の前に表を直す（S4-D§4.3）。表を直したコードの版を`V2_CODE_SHA`に上げる。
9. 版の更新：公開リポジトリで受領した版のSHAを、非公開リポジトリのworkflowの`V2_CODE_SHA`に書くコミット。
10. 保守の操作：gitの保存先で、C-4の復元・診断・採用が要るとき（`history.json`を取り出してローカルで操作し、公開として戻す）。Claudeと一緒に行う。
11. 巻戻しの確認（ブランチ保護が使えない場合）：実行の記録の`history_digest`が、前の朝から続いているか。
