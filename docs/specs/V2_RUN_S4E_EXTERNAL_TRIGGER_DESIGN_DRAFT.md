## 1. 結論

- GitHub の定時の実行（`schedule`）は、この非公開リポジトリで **3 時間半〜5 時間半遅れて**起きている。原因は GitHub 側の定時の起動で、こちらの設定では直せない（§2）。
- **外部の定時サービス（推奨：cron-job.org）が、日本時間の火〜土 7:40 と 8:40 に、GitHub の REST API で `v2-morning` の手動の実行（`workflow_dispatch`）を起こす**。workflow・コードは変えない。
- 起動に使うのは、**このリポジトリの Actions だけを書けるトークン（fine-grained PAT）1つ**。Rockyさんが作り、cron-job.org の設定に直接貼る。Claude は値を見ない。
- GitHub の `schedule` の 2 行は**予備として残す**（遅れて起きても、先に外部の起動が対象 D を処理していれば `SKIPPED_CLAIMED` で何もしない）。

- 設定は正しい：cron は `40 22 * * 1-5` と `40 23 * * 1-5`（毎時 0 分を避けた）、既定のブランチ（main）、workflow は `active`、YAML は正常（11-06T04:44Z の修正 f650155 以降）。

## 4. 仕組み

### 4.1 外部のジョブ（2 件）

| 項目 | 値 |
|---|---|
| URL | `https://api.github.com/repos/Rocky009-jp/soxl-alert-v2-run/actions/workflows/v2-morning.yml/dispatches` |
| 方法 | POST |
| ヘッダー | `Accept: application/vnd.github+json`、`Authorization: Bearer <トークン>`、`X-GitHub-Api-Version: 2022-11-28`、`Content-Type: application/json` |
| 本文 | `{"ref":"main","inputs":{"command":"morning","mode":"auto"}}` |
| 時刻 | ジョブ 1：UTC の月〜金 22:40。ジョブ 2：UTC の月〜金 23:40（＝日本時間の火〜土 7:40・8:40。日本に夏時間は無い） |
| 成功 | HTTP 2xx。本文に `return_run_details` を入れないので **204（本文なし）** が返る（P-02） |
| 失敗の知らせ | cron-job.org の失敗のメールを有効にする |

- `mode` は `auto`（`V2_MODE` に従う。E-5 の後も変えない。手順書 §4 と同じ）。
- 日曜・月曜の朝はジョブ自体が無い（cron と同じ）。米国の休場日の翌朝は、入口が `SKIPPED_CLAIMED` で何も送らない（今と同じ）。

### 4.2 トークン

- 種類：fine-grained personal access token。
- Repository access：**Only select repositories → `soxl-alert-v2-run` だけ**。
- 権限：**Actions: Read and write** だけ（Metadata: Read は自動で付く）。Contents・Secrets・Administration などは付けない。
- 期限：**1 年**を推奨し、期限の前に作り直す（期限切れは cron-job.org の失敗のメールと、9:30 の「来なければ止まっている」で気づく）。無期限も選べるが、漏れたときの影響が残り続けるので勧めない。
- 置き場所：cron-job.org の 2 件のジョブの `Authorization` ヘッダーだけ。リポジトリ・チャット・台帳・記録には書かない。Claude は値を見ない（設計第3版の秘密の扱いと同じ）。
- 作成・登録は Rockyさんのウェブの操作。Rockyさんのアカウントで作るので、dispatch の run の起動者は Rockyさんになり、**失敗のメールは Rockyさんに届く**（GitHub Docs：自分が起こした run の完了・失敗を通知する設定）。

### 4.3 GitHub の `schedule` の扱い

- **予備として残す**（推奨）。外部の起動が通っていれば、遅れて起きた `schedule` の run は同じ D に `SKIPPED_CLAIMED`（取得 0 回、約 1 秒、終了 0）。外部の起動が失敗した朝は、遅れても `schedule` が判定を出す（届くのは昼ごろ）。
- 同時に走っても、書く実行は同じ `v2-writer` に入り（`queue: max`）、同じ D の判定は 1 通まで（S4-C の比較交換・S4-D の固定）。
- Actions の使用：1 日 4 回（外部 2・`schedule` 2）× 約 1 分（切上げ）× 月 22 日 ≒ **月 90 分前後**（無料の枠 約 2,000 分の約 5%）。予備を外すと約 45 分。共有の枠を優先するなら外す案もある（D-3）。

### 4.4 変えないもの

- コード（2c7320f）、workflow（f650155）、`V2_MODE: dry`、台帳・参照の名前。公開リポジトリの main（31144d9）。
- 変えるのは手順書（§1 の通知の時刻の説明、§4 の手動の操作、トークンの期限の作り直し）と、試運転の基準 11 の測り方だけ。

## 5. 危険と扱い

| 危険 | 影響 | 扱い |
|---|---|---|
| トークンが漏れる | そのリポジトリの workflow の起動・**無効化（外部と予備の `schedule` の両方が止まる）**・取消し・再実行・実行記録の削除ができる。漏れる経路は主に cron-job.org のアカウント（ジョブの設定に平文で残る）。内容（Contents）・秘密は読めない。E-4 以後は `mode=live` で手動の実行を起こせる：`morning` は鍵で 1 日 1 通、`resend` は新しい `request_id` で同じ文面の再送が届き得る | 権限を Actions だけ・リポジトリ 1 つに絞る。疑わしいときはトークンを取り消して作り直す。受け入れる |
| cron-job.org が止まる・遅れる | その朝の外部の起動が無い | 予備の `schedule`（遅れて昼ごろ）、cron-job.org の失敗のメール、9:30 の「来なければ止まっている」 |
| トークンの期限切れ | 外部の起動が 401 で失敗 | cron-job.org の失敗のメール。期限の前に作り直す（1 年） |
| 25 回を超える失敗で自動無効化 | 以後の外部の起動が無い | 無効化のメールを有効にする |
| dispatch の 2 回と予備の `schedule` が重なる | 書く実行が並ぶ | `v2-writer`・`queue: max` で 1 つずつ。同じ D の判定は 1 通まで |

## 6. 試運転（E-3）への影響

- 基準 11「定時の遅れ」は、**外部の起動の予定時刻と run の作成時刻の差**で測る。2 回とも 1 時間以上遅れた朝が無いことは変えない。`schedule` の遅れは参考に記録する。
- 試運転の連続 10 セッションは、外部の起動を入れた最初の朝から数え直すかを D-4 で決める（推奨：数え直さない。基準 11 だけ外部の起動の後の朝で 10 セッションを満たす）。
- 外部の起動の後は、**7:40 が F&G の記録の締切として実際に効く**（これまでの朝は定時が数時間遅れたので、記録は必ず実行の前に済んでいた）。E-3 の記録には、F&G の記入（push）の時刻と 1 回目の run の作成の時刻を並べて書く（P-04）。
- 遅れの原因を分けるため、記録に cron-job.org の実行履歴の「実行の時刻」と「応答の状態」、run の `created_at`、ジョブの `started_at` を並べる。cron-job.org の履歴は Rockyさんが画面で見る（2 日で消えるので、遅れた朝はその日のうちに）（P-05）。
- 外部の起動を入れるまでの朝は、今のとおり（`schedule` が遅れて判定を出す。台帳はチャットで受けて 7:40 までに記入）。

## 7. 入れる手順（採用の後。Rockyさんの操作）

1. GitHub の Settings → Developer settings → Fine-grained tokens → Generate new token。名前 `v2-morning-dispatch`、期限 1 年、Only select repositories で `soxl-alert-v2-run`、Permissions の Actions を Read and write。作成後の値は一度だけ表示される。
2. cron-job.org でアカウントを作り、§4.1 の 2 件のジョブを作る（タイムゾーン UTC、または Asia/Tokyo で 7:40・8:40 の火〜土）。`Authorization` に `Bearer ` に続けてトークンを貼る。失敗のメール・自動無効化のメールを有効にする。cron-job.org のパスワードは他と使い回さず、2 段階の認証があれば有効にする（P-03）。
3. ジョブ 1 の「テスト実行」を 1 回押す。**押すのは、その朝の 2 回の実行が終わった後、日本時間 10:00〜22:00**（新しい D を処理させない。7:00〜7:40 に押すと、台帳に F&G が無い D が「F&G 未記録」で確定する）。**結果は `SKIPPED_CLAIMED`（取得 0 回）になるのが正しい**（N-01）。Claude が run（起動者・入力・作成の時刻）を確かめる。
    - cron-job.org の実行履歴で応答が 2xx（204）かを確かめる。**403 なら（User-Agent が付いていない等）、案 B（Cloudflare Workers の Cron Triggers）に切り替える**。切り替えのために設計をやり直さない（同じ URL・ヘッダー・本文を Workers から送る）（P-01）。
4. 次の朝の 7:40・8:40 に、外部の起動の run が数分以内に作られたかを Claude が確かめて記録する。
