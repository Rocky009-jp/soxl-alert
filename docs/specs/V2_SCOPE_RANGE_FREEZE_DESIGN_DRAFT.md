B-5b設計（5d21c10）のD-3で「次の段階（CONSUME、S3-C）の前に別に設計する」と提案した方式を、Rockyさんの承認を受けて具体化する。今回の作業は設計書と限定実装依頼書の作成まで。文書の保存、推奨、一時環境での試行の合格を、実装の承認と扱わない。作成担当はClaude Opus 5.5、effort high。

## 0. 要約

- **問題**：git差分で範囲を監査する範囲試験5本（b17、r3_07、r4_09、d5_08、a5_08）は、どれも「自分の段階の開始点STARTから、今のHEADまで」を比べる。後の段階が古いファイルを1つ変えるたびに、古い範囲試験すべての許可を広げる補正が要る。さらに新しい範囲試験は古い範囲試験の差分を固定文字列で持つので、補正の補正が段階ごとに積み重なる。a5_08は1867行あり、うち約1450行が前の段階の試験の差分を書き写した文字列である。
- **推奨する方式（D-1の案a、受領済み範囲の固定）**：受領した各範囲試験の差分監査（FilesChangedクラス）を、「START→その段階の受領時の最終コミットEND」の固定した範囲に閉じる。内容は受領時の文字のまま戻し、HEADと作業ツリーの読取りをENDの読取りに置き換えるだけにする。5本の範囲はadfdf765→b328844→d82a5ce→ac21980→c8ba08f→b626c98と隙間なくつながる。今のHEADは、まだ受領していない最新の段階の範囲試験だけが監査する。
- **今後の規則**：新しい範囲試験は`END = None`（未受領）で書き、次の段階がそのENDに受領時のSHAを1行で入れて固定する。新しい段階が古い範囲試験を直すのは、その段階が古いパッケージ自体を変えるときの、静的な検査（import・種別名などの規則）だけになる。範囲の鎖（STARTとENDが隙間なくつながり、開いている範囲が1つ以下）を別の試験が自動で確かめる。
- **一時環境での試行**：b626c98のコピー（pushしないローカルコミット）で5本を固定した。既存10スイート1634件がLinux・Python 3.13.18で全件合格した。固定で変わる文字は、受領時の文字に対して5本合計91行（HEAD→END、作業ツリー→END）だけであることも確かめた。次の段階を模した変更（古いランタイム2本とB-5bのパッケージを1行ずつ変え、新しいパッケージ・試験・結果文書を足す）で比べると、固定しない場合は5本すべてで計11件失敗した。固定した場合は0件だった（§7）。
- 採否はD-1〜D-4の一組（§9）。

- **大きさ**：B-5bでの補正はd5_08だけで追加374行・削除87行だった（B-5b設計§7.3）。a5_08のPINNED_TESTSは約1450行ある。このまま次の段階で同じ方式を取ると、a5_08を含む6本の補正と、その差分の書き写しがさらに増える。

## 3. 重複している監査

後の段階の範囲試験は、自分のSTARTから見て、許可した変更以外がすべてblob単位で同じであることを確かめている（d5_08・a5_08の「everything else is identical」「blob identical」の各試験）。古い範囲試験がSTART→HEADを見続けることで得ている保護は、次の二つの組で置き換えられる。

1. 古い範囲（START→END）は受領済みの履歴であり、固定した範囲として確かめ直せる。
2. ENDより後の変更は、次の段階の範囲試験が自分のSTART（＝前の段階のEND）から監査する。

STARTとENDが隙間なくつながっていれば、adfdf765から今のHEADまでのすべての変更が、どれか一つの範囲試験に監査される。古い範囲試験が後の段階の変更を見ることは重複であり、補正の連鎖の原因になっている。

## 4. 方式の比較（D-1）

| 案 | 内容 | 評価 |
|---|---|---|
| **(a) 受領済み範囲の固定（推奨）** | FilesChangedをSTART→ENDの固定範囲にし、受領時の文字に戻す。読取りだけをENDへ置き換える。今後の範囲試験は`END = None`で書き、次の段階で1行で固定する | 1回だけの変換で連鎖が止まる。受領時の監査の文字がそのまま残るので、レビューで読む量が少ない。一時環境で試行済み（§7） |
| (b) 今のまま続ける | 前例どおり、段階ごとに古い範囲試験と固定文字列を補正する | 試行で動くことは分かっているが、補正の量が段階ごとに増える。レビューの負担と誤りの機会が増える |
| (c) 共通の範囲台帳 | 段階ごとの許可を1つの台帳（データ）にまとめ、1本の共通監査で全段階を見る | 構造としては整うが、受領済みの5本のFilesChangedを書き直すことになり、受領時の監査と同じであることを示す負担が大きい。試行していない |

## 5. 固定の中身（D-2）

### 5.1 範囲とEND

| 範囲試験 | START | END（完全SHA） |
|---|---|---|
| b17 | adfdf765aeca0d01c8f10b596a6fac59d7c1a07e | b328844fdeda235cf95bf7851ba9e3d7d55aa7bb |
| r3_07 | b328844（r3_helpers.FIXED_START） | d82a5ced64658c2e736b82b1a2f1925636055417 |
| r4_09 | d82a5ce（r4_helpers.FIXED_START） | ac219801d290ebb59b720f37a086103b6e1251c9 |
| d5_08 | ac219801d290ebb59b720f37a086103b6e1251c9 | c8ba08f15ea28248a9fe7924f32ce136fc16d5e6 |
| a5_08 | c8ba08f15ea28248a9fe7924f32ce136fc16d5e6 | b626c98af5f01bc94e7b41d86aadde9663695eb9 |

ENDは、その段階の結果文書を含む最終コミットで、次の段階のSTARTと同じ値にする。こうすると範囲が隙間なくつながる。結果文書だけを足したコミットも範囲に入る。各段階の範囲試験は、結果文書のパスを新規の許可に含めている。

### 5.2 各ファイルで変えるもの

固定する部分は次のとおり。
- 範囲試験のFilesChangedクラス。
- FilesChangedだけが使うモジュール定数（r4_09のB17_REMOVED、B17_ADDED、B17_HUNKS、R307_REMOVED、R307_ADDED、R307_HUNKSの6つ、d5_08のPINNED）。

これらは**ENDの時点の文字に戻し**、次の置換だけを行う。
1. コードとしての文字列"HEAD"（引数そのもの）をENDにする。固定文字列の中に書かれた"HEAD"という文字は変えない（トークン単位で置き換える。r3_07の固定差分の中に`START, "HEAD"`という文字があるため）。
2. 作業ツリーのblob（`git hash-object path`）を、ENDのblob（`git rev-parse END:path`）にする。
3. 作業ツリーのファイル読取り（`open(os.path.join(ROOT, …))`）を、ENDのファイル（`git show END:path`）にする。with文の1行だけを`io.StringIO(git_show_at_end(path))`に替え、本体は変えない。
4. 作業ツリーの一覧（a5_08の`os.listdir(ROOT/v2_history)`）を、ENDの一覧（`git ls-tree --name-only END v2_history/`）にする。
5. setUpで、STARTに加えてENDのコミットが無ければskipする（既存の「commit is not available」と同じ扱い）。

a5_08は今がENDの時点の文字なので、置換だけを行う。a5_08ではモジュール関数`git`と`current_text`も読取りに使うので、これらも同じ置換の対象にする。

固定しない部分（今の文字のまま）：Runtime、Imports、NoSideEffects、PathJudgementの各クラス、パス判定のモジュール関数、KIND_CONSTANTSなどFilesChanged以外も使う定数。これらはそのパッケージの今のソースや純粋な関数を検査するもので、そのパッケージを後の段階が変えたときに直す必要がある。直すのはその段階の範囲試験が監査する（§6）。

各ファイルに加えるもの：
- `END = "<完全SHA>"`の1行（STARTの直後）。
- `import io`。
- ENDのファイルを読むモジュール関数`git_show_at_end(path)`を1つ。

### 5.3 固定後に言えること・言えないこと

- 言えること：受領した範囲START→ENDの変更が、その段階の監査の規則を満たすこと。git履歴が書き換えられていなければ、この結果は何度実行しても同じになる。
- 言えないこと：古い範囲試験は、END以降の変更を見ない。END以降は、次の段階の範囲試験と範囲の鎖の試験（§6.3）が監査する。古い範囲試験の合格を、今のHEADの監査と書かない。
- 履歴が無い環境（`git archive`のツリーなど）では、従来どおりFilesChangedはskipになる。件数を比べるときは完全なクローンで実行する（B-5b再レビュー003b6dc §3の注意と同じ）。

## 6. 今後の規則（D-3）

### 6.1 新しい範囲試験の書き方

    START = "<前の段階のEND>"
    END = None          # 受領前。次の段階が受領時の最終コミットの完全SHAを入れる
    REV = END or "HEAD"

- git差分はすべて`START`→`REV`で取る。ファイルの中身・blob・一覧も`REV`から読む（作業ツリーを読まない）。未受領の間はHEADの確定状態を見ることになる。従来の試験も「committed state」を比べていたので、意味は変わらない。
- 前の段階の範囲試験の差分を固定文字列で書き写さない。前の段階の範囲試験を直したときは、その削除行・追加行・ハンクを**自分の段階の差分として**固定する（前の段階の固定文字列を作り直さない）。

### 6.2 次の段階がすること

1. 前の段階の範囲試験の`END = None`を、受領時の最終コミットの完全SHAに替える（1行）。
2. 自分の段階が古いパッケージを変えるなら、そのパッケージの範囲試験の静的な検査を必要な箇所だけ直す（例：種別名を加えたらKIND_CONSTANTS）。
3. 自分の範囲試験で、1と2の差分と自分の変更を監査する。

これで次の段階の補正は「1行＋静的な検査の必要箇所」になる。範囲試験の数に比例して増えず、書き写しの連鎖も起きない。

### 6.3 範囲の鎖の試験

tests/配下の範囲試験（モジュールのSTARTとFilesChangedクラスを持つ試験）を自動で探し、ASTでSTART・ENDを読む（r3_07・r4_09のようにヘルパーのFIXED_STARTを参照する形も読む）。次を確かめる。

- STARTが重複しない。どの範囲のENDでもないSTARTがちょうど1つある（鎖の始まり＝adfdf765）。
- 始まりから`END`をたどると、すべての範囲試験を1回ずつ通る。各STARTはENDの祖先、各ENDはHEADの祖先（`git merge-base --is-ancestor`）。
- `END = None`の範囲は、鎖の最後の1つだけ。固定の段階の後は、その段階の新しい範囲試験がこれに当たる。
- 鎖の始まりのコミットがあるのに、途中のSTART・ENDが無い場合は失敗にする（一部だけ取れた履歴を合格にしない）。履歴が全く無い場合だけskip。

この試験は範囲試験を自動で探すので、段階が増えても書き換えが要らない。一時環境で、固定後の5本が隙間のない鎖になることと、固定前（ENDが無い）は鎖にならないことを確認した（§7）。

## 8. 固定の監査（新しい範囲試験）

固定の段階の範囲試験を、新しいディレクトリtests/v2_scope_chain/に置く（D-4）。この試験も§6.1の形で書く（START＝b626c98、END＝None）。
