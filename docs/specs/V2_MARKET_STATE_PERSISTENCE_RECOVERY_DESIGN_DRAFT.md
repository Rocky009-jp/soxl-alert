## 0. 要約

推奨案の骨子は次の8点。いずれも未採用。

1. **保存単位を「現在状態」と「追記のみの遷移記録」の2つにする。** 現在状態は今のコアの`MarketState`（armed、連続数、前日normal_raw、対象D、固定decision、基点）に、通番と直前の遷移記録の指紋を足したもの。遷移記録は1回の消費（DのdecisionをMarketStateへ適用して確定すること）や明示的な復旧操作ごとに1件を足し、書き換えない。
2. **保存先は、非公開の別リポジトリ（案B）を推奨する**（第2版で改めた。Rockyさんのレビューでも同じ推奨）。gitの参照更新は「早送りだけ許す」ことで比較交換（CAS）として働く。台帳（F&Gの観測記録）の置き場所（U-11）と一緒に決める。同じ公開リポジトリの状態専用ブランチ（案A）は代替案。
3. **1回の実行の順序を固定する。** 状態を読む → 検査する → 未処理のセッションを古い順に1件ずつ消費して保存 → 最新Dを評価 → 通知の送信権を取る → 送信 → 送信結果を記録。状態の保存は通知の成否を待たず、通知の失敗で巻き戻さない。
4. **二重消費の防止は、「有効な履歴の中でDごとに1件だけ」の遷移記録と、保存時の比較交換で行う。** 同じDの再実行は、保存済みの基点と確定入力から再計算し、結果が一致すれば何も足さない。一致しなければ止める。
5. **遷移記録に、再計算に要る入力そのもの（decisionの値・時刻・対象D、判定に使った市場の値、セッション時刻）を保存する。** 台帳が後から変更・消失しても、消費済みのDを再計算・検証できる。
6. **不明な状態では止める。** 状態が無い・壊れている・不変条件に反する・台帳と食い違う、のいずれでも、黙って初期化・巻き戻し・上書きをしない。復旧は、ユーザーが明示的に選ぶ手順（§4.3）として、新しい遷移記録を足す形でだけ行う。欠測宣言やACKは、対象の観測を指紋で特定し、コアへ渡す観測集合から除く形で効かせる（生の台帳は変えない）。
7. **通知は、送信権を持つ1つの実行だけが送る。** 送信前に「新規作成だけ」の意図の記録を保存し、自分の記録が保存された実行だけが送る。結果は「送った」「送っていないと確定」「不明」で記録し、不明なら自動で再送しない。
8. **P-04（状態の整合性）とP-06（record_idの制約）は、読込時の検査として設計に組み込む。** 現在状態と基点は別の規則で検査する。実装する場合はコアの変更になるため、別の承認が要る。

ユーザーに残る判断は§8の未決事項（U-01〜U-14）。

### 1.2 用語

- **台帳**：ユーザーが目視したF&Gの観測記録（`docs/templates/FG_OBSERVATION_TEMPLATE.csv`の様式）。置き場所とランナーへの渡し方は未決（U-11）。
- **消費**：あるDについて、decisionを状態へ適用し、遷移記録として保存すること。有効な履歴の中で、Dごとに1回だけ。
- **ランナー**：後工程で作る実行役。保存先から状態を読み、コアを呼び、保存と通知を順に行う。本書はランナーと保存先アダプタの設計で、実装はしない。
- **遷移記録**：1回の消費、または明示的な復旧操作の内容を書いた、書き換えない記録。
- **有効な履歴**：現在状態から親をたどって得られる遷移記録の列（§2.6）。**退避した履歴**は、復元で有効でなくなったが、消さずに残す遷移記録。
- **確定入力**：消費のときに実際に使った入力の内容。遷移記録に保存する（§2.3）。
- **観測の指紋**：コアの`Observation.fingerprint()`（record_id、状態、役割、値、UTCに正規化した観測時刻、対象DのSHA-256）。ランナーは同じ関数を使い、自前で計算し直さない。

## 2. 保存する状態と整合性検査

### 2.1 項目の関係

| 項目 | 意味 | いつ決まるか | 関係 |
|---|---|---|---|
| 対象D（`as_of_d`） | 最後に消費したセッション | 消費時 | `fixed_decision.d`と一致。`base.as_of_d`より後 |
| armed | 極端恐怖の発火権 | 消費時（F&G<25でfalse、≥30が3連続でtrue、欠測でUNKNOWN） | 連続数≥3ならtrue |
| 連続数 | 確認済みの連続観測（F&G≥30）の数 | 消費時（≥30で+1、それ以外0、欠測で0にしてから当日分を数える） | 1以上なら直前のF&Gは30以上なので前日normal_rawはfalse |
| 前日normal_raw | Dのnormal_raw（次のDから見た前日） | 消費時 | trueなら連続数は0 |
| 固定decision | Dで消費したdecisionの`record_id`と指紋 | 消費時 | 指紋は観測の指紋（§1.2） |
| 基点（`base`） | Dを消費する直前の状態の写し。`as_of_d`・armed・連続数・前日normal_rawだけを持ち、`fixed_decision`と`base`は持たない | 消費時 | 同じDの再実行は「基点＋確定入力」から再計算する |
| 判定入力・確定入力（新設案） | Dの判定に実際に使った値と、decisionの内容 | 消費時 | 再実行や事後の検証で、同じ入力から同じ結果になるかを確かめる（§2.3） |

ポイントは、**現在状態は「基点に、Dの確定入力を適用した結果」と一致しなければならない**こと。現在のコアは、同じDの再実行のときだけ実質的にこれを確かめる（再計算して返す）が、保存済みの結果と比べる処理は無い。ランナーは再計算した結果と保存済みの状態を比べ、違えば止める（§4、E-10）。

### 2.2 保存単位

| ファイル | 内容 | 書き方 |
|---|---|---|
| 現在状態 `state.json` | 形式名、先頭の通番、先頭の遷移記録のパスと指紋、`MarketState.to_dict()` | 遷移ごとに新しい内容で置き換える（同じコミットで遷移記録と一緒に） |
| 遷移記録 `entries/NNNNNN-<種別>[-<D>].json` | 1回の消費、または明示的な操作 | 追記だけ。既存のファイルは変更・削除しない。退避しても消さない |
| 通知の意図 `outbox/<D>-<種別>.claim.json` | 送信権の記録（§5.3） | 新規作成だけ |
| 通知の結果 `outbox/<D>-<種別>.result.json` | 送信の結果 | 新規作成だけ。送信権を持つ実行だけが書く |
| 再送の意図と結果 `outbox/<D>-<種別>.resend-<resend_request_id>.claim.json`／`.result.json` | 手動の再送1件の送信権と結果（§5.3） | 新規作成だけ。同じ依頼は同じパス |
| 台帳の写し `ledger_snapshots/<sha256>.json`（U-11の決め方による） | ランナーが読んだ台帳の6列の正規化した内容 | 内容が変わったときだけ追加 |

遷移記録の種別：GENESIS、APPLY、RECOVERY_RESTORE、DECLARE_MISSING、ACK、RESTART_UNKNOWN、（CORRECTION、未整備）。

全ての遷移記録は、**その記録の後の市場状態**（`state_after`、`MarketState.to_dict()`の形）を持つ（第3版で追加）。市場状態を変える種別と変えない種別は次のとおり。

| 種別 | 市場状態 | `state_after` |
|---|---|---|
| GENESIS、RESTART_UNKNOWN | 初期状態にする | 初期状態 |
| APPLY | Dを消費して進める | 消費後の状態（`next_state`と同じ） |

| ACK、DECLARE_MISSING | 変えない | 親の記録の`state_after`と同じ（I-15） |

### 2.3 判定入力と確定入力（第2版で改訂）

初版は「判定入力の指紋」だけを保存する案だったが、指紋からは元の値・時刻を復元できない。第2版では、**再計算に要る入力そのものを遷移記録に保存する**。

| 区分 | 保存する内容 | 用途 |
|---|---|---|
| decisionの確定入力（`decision_record`） | record_id、状態、役割、F&Gの値、観測時刻（元の表記とUTC）、対象D、指紋 | 台帳が変更・消失しても、消費に使った観測を取り戻せる。保存した内容から指紋を計算し直し、一致を確かめる（I-11） |
| 市場の判定入力（`rule_inputs`） | D行のSOXX・SMA200・RSI・前日RSI・SHD、前日行のSOXX・SMA200・RSI・SHD、前日の市場側normal | 遷移の再計算に要る市場の値。指標は前史全体から計算されるので、前史そのものではなく計算後の値を持つ |
| セッション時刻（`sessions`） | 前日・D・翌のセッションの日付と時刻 | decisionの窓（close(D)以上、open(next(D))未満）と欠測の判定を再現する |
| 基点 | `next_state.base` | 再計算の出発点 |
| 版 | コアのコミットSHA | 規則の版が違う再計算を区別する |
| 台帳の参照（`ledger_ref`） | 台帳を読んだときのコミットSHAとパス、または台帳の写しの指紋 | その時点で見えていた台帳全体を取り戻す（台帳がgitにあればその履歴、なければ`ledger_snapshots/`） |
| 参考の指紋（`series_meta`） | 入力ファイルの指紋 | 事後の調査用。新しい日の行が足されるだけで毎日変わるので、再実行の一致判定には使わない |

再計算の方法：

- **推奨案**：「基点・decisionの確定入力・市場の判定入力」だけから次状態と判定結果を返す純粋な関数をコアに設け、遷移の再計算と検証は保存した値だけで行う。今のコアは`evaluate_day`の中に遷移の計算があり、市場系列とセッション列を渡す必要があるため、**コアの変更**になる（§9、別承認）。
- **それまでの代替**：保存した`decision_record`をコアへ渡す観測として使い、市場系列は再実行時のものを使って`evaluate_day`を呼ぶ。再計算した`rule_inputs`が保存値と違えば、価格改訂か入力の誤りとして止める（E-10）。この方法では、市場系列が手元に無いと再計算できない。

市場系列そのもの（2010年からの前史）は、毎日1行ずつ変わり容量が大きいので、遷移ごとには保存しない。調整後価格の改訂（分配落ち等）で過去のRSIやSMAが変わることがある。推奨案は「**消費済みの遷移は書き換えない**。改訂は以後のDにだけ効く。消費済みDの再計算が保存値と違えば止めて知らせる」（U-07）。

decisionの値と観測時刻を保存すると、保存先を見られる人には日々の観測記録が見える。案B（非公開）では問題になりにくいが、案A（公開）ではこれも公開される（§3.2）。

### 2.4 不変条件（P-04、第2版で現在状態と基点を分けた）

初版のI-01（`as_of_d`の有無と`fixed_decision`・`base`の有無が一致）は、基点に当てはめると正常な状態を拒否する。コアは基点の`as_of_d`を残し、`fixed_decision`と`base`を落として保存するため、正常な基点は「`as_of_d`あり・`fixed_decision`なし・`base`なし」になる。第2版では、現在状態と基点を別の規則で検査する。

違反は`state_invalid`として止める（終了コード1、状態不変、初期化しない）。

**現在状態の検査**（`state.json`の最上位の`MarketState`だけに当てはめる。読込時に毎回）

| ID | 条件 |
|---|---|
| I-01 | `as_of_d`が無い ⇔ `fixed_decision`が無い ⇔ `base`が無い |
| I-02 | `as_of_d`が無いなら、armed=UNKNOWN、連続数0、前日normal_raw=UNKNOWN（初期状態そのもの） |
| I-03 | `fixed_decision.d == as_of_d` |
| I-04 | `base.as_of_d`は無いか、`as_of_d`より前 |
| I-05 | 連続数≥3ならarmed=TRUE |
| I-06 | 連続数≥1なら前日normal_raw=FALSE（前日normal_raw=TRUEなら連続数0） |
| I-07 | `fixed_decision.fingerprint`は小文字16進64桁、`fixed_decision.record_id`は§2.5の文字種 |

**基点の検査**（`base`だけに当てはめる。読込時に毎回）

| ID | 条件 |
|---|---|
| IB-01 | `fixed_decision`と`base`を持たない（コアの写し方どおり）。`as_of_d`はあってよい |
| IB-02 | `as_of_d`が無いなら、初期状態そのもの（基点がGENESISかRESTART_UNKNOWN直後の状態） |
| IB-03 | 連続数≥3ならarmed=TRUE、連続数≥1なら前日normal_raw=FALSE（基点も、かつての現在状態なので同じ算術の関係を満たす） |
| IB-04 | **現在状態を作ったAPPLY**（有効な履歴を先頭からさかのぼって最初に見つかるAPPLY。RECOVERY_RESTOREをまたぐ場合は、復元点を作ったAPPLYか、その後に消費し直したAPPLY）の、**親の記録の`state_after`**から`fixed_decision`と`base`を落としたものと一致する。ACKと欠測宣言は市場状態を変えないので、間に何件あっても比較の相手は変わらない（第3版で改めた。第2版の「1つ前の遷移記録」との比較は、APPLYの後にACKを足すだけで落ちる） |

IB-01〜IB-03は状態ファイル単体で確かめられる。IB-04は遷移記録が要る。現在状態が初期状態（GENESISかRESTART_UNKNOWNの後に消費が無い）なら`base`は無いので、IB-01〜IB-04は当てはめない。

**保存先の検査**（遷移記録と合わせて確かめる）

| ID | 条件 | 確かめる時 |
|---|---|---|
| I-08 | 遷移記録の通番が1から欠けずに増え、`state.json`の先頭の通番・指紋が最後の遷移記録と一致 | 読込 |

### 2.5 record_idの制約（P-06）

`fixed_decision`と`decision_record`にはrecord_idがそのまま入る。台帳の様式には`source_url`列があり、取り違えが起こり得る。保存先を非公開にしても、通知本文やログへの混入を防ぐために制約を置く。

- **推奨案**：record_idを`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`（英数字で始まり、英数字・ピリオド・下線・ハイフン、最大64文字）に限る。台帳の読込時と状態の読込時の両方で検査し、外れたら`record_id_invalid`（入力エラー、値は表示しない）。実観測は0件なので、移行の対象は無い。
- **代替案1**：状態にはrecord_idのSHA-256だけを持つ。漏えいは防げるが、復旧のときに人が台帳の行と照合しにくい。
- **代替案2**：運用ルール（「record_idに秘密やURLを書かない」）だけにする。検査が無いので、P-06の懸念が残る。

### 2.6 有効な履歴と退避した履歴（第2版で新設）

初版のR-2は「検証に通る過去の遷移へ戻し、その後のDを台帳から再び消費する」としていたが、これは「Dごとに遷移記録1件」と衝突する。第2版では、遷移記録を消さずに、**どの遷移記録が今の状態を作っているか**を明示する。

- **通番（`seq`）**：全ての遷移記録に通して振る。退避した記録も含めて欠けず、使い回さない（I-08）。
- **親（`parent_seq`）**：その遷移記録が前提にした、有効な履歴の1つ前の記録。通常は直前の通番。
- **有効な履歴**：先頭（`state.json`が指す最後の遷移記録）から`parent_seq`をたどってGENESISまで至る列。現在状態はこの列だけから決まる。
- **退避した履歴**：RECOVERY_RESTOREが`superseded_seqs`で名指しした記録。消さずに残し、調査には使うが、状態の再生・重複の検査・通知の判断には使わない。
- **「Dごとに1件」の範囲**：有効な履歴の中だけ（I-09）。退避した履歴に同じDのAPPLYがあっても、有効な履歴に1件だけなら二重消費ではない。

RECOVERY_RESTOREの記録（例）：

```json
{"seq": 58, "parent_seq": 50, "kind": "RECOVERY_RESTORE",
 "superseded_seqs": [51, 52, 53, 54, 55, 56, 57],
 "restore_point_state_sha256": "…", "state_after": "<復元点の記録のstate_after>",
 "plan_sha256": "…", "reason": "…",
 "operator": "user-explicit", "created_at": "…"}
```

規則：

1. 復元点（`parent_seq`）は有効な履歴の中の記録に限る。退避した記録へは戻らない。
2. `superseded_seqs`は、復元点の次から古い先頭までの有効な記録をちょうど全部含む。
3. 復元の後で同じDを消費し直すときは、新しいAPPLYを有効な履歴に足し、退避した同じDの記録の通番を`replaces_superseded_seq`に、内容が同じかどうかを`same_as_superseded`に書く。
4. 復元とその後の消費し直しは、通知を送らない。通知の記録（outbox）は有効な履歴と独立していて、過去のDの通知を作り直さない（§5）。
5. RESTART_UNKNOWNは何も退避しない。有効な履歴を続けたまま状態を初期状態に戻し、`resume_after`（このD以前は処理しない）を持つ。`resume_after`は有効な履歴の最後の消費D以上とし、以後のAPPLYの対象Dが過去と重ならないようにする。GENESISも同じく、最初に処理するセッションを決める`start_after`を持つ。

### 2.7 コアへ渡す観測集合（第2版で新設）

コアは渡された観測をすべて検査し、過去の日の衝突でも止まる（§1.1）。欠測宣言やACKを遷移記録に足すだけでは、その観測が入力に残る限り、コアは同じ衝突を検出し続ける。そこで、**生の台帳は変えずに、ランナーがコアへ渡す観測集合を決める**。

組み立ての手順（ランナー、実行ごと。第3版で順序を改めた）：

1. **読む**：台帳を特定の版（gitならコミットSHA）で読み、コアが使う6列（record_id、状態、役割、値、観測時刻、対象D）だけを取り出す。読んだ版を`ledger_ref`に記録する。
2. **解析する**：コアの`parse_observation`で各行を解析し、観測の指紋を得る。解析できない行は入力エラーで止める（除外の対象にもできない。行を直す）。
3. **解決記録を検証する**：有効な履歴にあるACKとDECLARE_MISSINGのそれぞれについて、次を確かめる。違えば`state_invalid`で止める。
   - ACK（ADDED、CHANGED、ROW_REMOVED）：消費済みのDについての食い違い。対象Dが有効な履歴のAPPLYであること。ACKが持つ「適用済みの固定decisionの指紋」（`applied_fingerprint`）が、そのAPPLYの`fixed_decision.fingerprint`と一致し、そのAPPLYの`decision_record`から計算し直した指紋（I-11）とも一致すること。
   - ACK（LATE、第4版で別規則にした）：欠測として扱ったDに、後からdecisionが現れた食い違い。欠測日は未適用なので、固定decisionの指紋は存在しない。代わりに次を確かめる。
     - `missing_ref_seq`（欠測を記録した遷移記録の通番）が有効な履歴にあり、その記録が対象Dを欠測として記録していること。該当するのは、`skipped_sessions`に対象Dを含むAPPLYか、対象DのDECLARE_MISSING。
     - 対象Dに、有効な履歴のAPPLYが無いこと。
     - `applied_fingerprint`を持たないこと（持っていれば不正）。
     - 除外する観測の指紋の一覧（`record_fingerprints`）が空でないこと。
     - LATEのACKは補完をしない（手順5の対象外）。
   - DECLARE_MISSING：対象DにAPPLYが無いこと（I-09）。
4. **除外する**：検証に通った解決記録が名指しした指紋の集合に**完全に一致する**行だけを除く。指紋が1文字でも違う行（後から内容を変えた行）は除かれない。
5. **補う**：消費済みの各Dについて、除外後の集合に固定decisionと同じ指紋の行が無く、かつ、そのDについて「消費に使った行が失われた」ことを確認したACKが手順3を通っているときだけ、そのAPPLYの`decision_record`から行を1件補う。該当するACKは次の2種類。
   - ROW_REMOVED：消費に使った行が台帳から消えた。
   - CHANGED：消費に使った行が書き換えられ、元の内容の行が台帳に無い。書き換え後の行の指紋をACKが名指しして除外し（手順4）、元の内容をここで補う。元の行がまだ台帳に残っている場合（同じrecord_idの別の版が足された場合）は、補わない。
   固定decisionと同じ指紋の行が既にあるときは補わない（二重にしない）。ACKが無ければ補わず、次の手順で止まる。
6. **最終の観測集合を検査する**：除外と補完の後の集合について、
   - 有効な履歴で消費済みの各Dに、固定decisionと同じ指紋の行がちょうど1件あり、それ以外にそのDを対象とするdecision行、またはそのDの窓内に観測されたdecision行が無いこと。違えばE-16で止める。
   - 欠測として飛ばしたD（`skipped_sessions`）とDECLARE_MISSINGのDに、decision行が無いこと。違えばE-17で止める。
7. **渡す**：この集合をコアへ渡す。どの解決記録を使ったか、どのDを補ったかを、次に足す遷移記録の`exclusions_applied`と`supplemented`に書く。

第2版は、最終の検査（第2版の手順4）を補完（第2版の手順5）より先に置いていたため、ROW_REMOVEDのACKがあっても補完に到達できなかった。第3版では、ACKを検証してから補完し、その後で最終の集合を検査する。

除外を作る記録（ユーザーの明示操作だけで足す）：

| 種別 | 持つもの | 効き方 |
|---|---|---|
| DECLARE_MISSING | 対象D、そのDのdecision行の指紋の一覧、それを見た台帳の版、理由 | 一覧の行をコアへ渡さない。市場状態は変えない（`state_after`は親と同じ）。Dにはdecisionが無いので、次に消費するセッションでコアの欠測規則が効く（`gap=true`、`skipped_sessions`にD）。後から同じDに一覧に無い指紋のdecision行が現れたら、E-17で止める |
| ACK | 対象D、食い違いの種類（ADDED、CHANGED、ROW_REMOVED、LATE）、確認した行の指紋の一覧（ROW_REMOVEDでは空、LATEでは空にしない）、ADDED・CHANGED・ROW_REMOVEDでは適用済みの固定decisionの指紋（`applied_fingerprint`）、LATEでは欠測を記録した遷移記録の通番（`missing_ref_seq`）、台帳の版、理由 | 一覧の行をコアへ渡さない。ROW_REMOVEDと、元の行が失われたCHANGEDは、手順5で確定入力から補う。市場状態は変えない（`state_after`は親と同じ）。一覧に無い指紋の行が新たに食い違えば、また止める |

この作りで、生の台帳はユーザーが書いたまま残り、どの観測をなぜ使わなかったかは遷移記録から追える。除外は指紋にひも付くので、同じ行を後から書き換えると、確認が自動で引き継がれることはない。

同じrecord_idで内容違いの2行がある場合（`record_id_conflict`）、どちらかを除外すればコアは通るが、どちらを使うかを選ぶことは訂正に当たる（U-03）。推奨は、台帳を直すか、そのDをDECLARE_MISSINGで両方除外すること。

### 2.8 追いつきの開始位置と境界（第4版で新設）

ランナーが追いつきを始めるセッションは、次の規則で決める。

| 現在状態 | 開始位置 |
|---|---|
| `as_of_d`がある | `as_of_d`の次のセッション |
| `as_of_d`が無い（初期状態） | 有効な履歴を先頭からさかのぼって**最初に見つかる、市場状態を初期化した記録**の境界の次のセッション。GENESISなら`start_after`、RESTART_UNKNOWNなら`resume_after` |

- ACKとDECLARE_MISSINGは市場状態を変えない（I-15）ので、さかのぼるときに読み飛ばす。再初期化の後にACKや欠測宣言を何件足しても、境界は動かない。
- RECOVERY_RESTOREで初期状態の時点へ戻した場合も、親をたどって、その時点の状態を作ったGENESISかRESTART_UNKNOWNの境界を使う。
- `as_of_d`が無いのに、さかのぼって初期化の記録が見つからない、または見つかった記録に境界が無い場合は`state_invalid`で止める（自動で開始位置を推測しない）。
- 境界以前のセッションは処理しない。台帳に境界以前のdecision行があっても消費しない（行はコアへ渡す観測集合に残るので、解析と衝突の検査は受ける）。
- 境界の後で最初のAPPLYでは、基点の`as_of_d`が無いので、コアは欠測（`gap`）を報告しない（初期状態は既にarmed不明・連続数0・前日normal_raw不明で、欠測の扱いと同じになる）。ただし、ランナーは境界の次からDの前までのdecisionの無いセッションを`skipped_sessions`に記録し、E-17（LATE）の検出に使う。

### 3.2 推奨案B の理由と条件（第2版で改めた）

初版は案Aを推奨したが、第2版では案Bに改める。Rockyさんのレビュー（2026-10-28）の推奨と同じで、理由は「日々の観測・運用記録を公開する必要性が現状ではない」こと。加えて、第2版で遷移記録にdecisionの値と観測時刻を保存する方針（§2.3）にしたため、案Aでは公開される内容が増える。**どちらも採用済みではない**（U-01）。

案Bの理由：

- 比較交換が、新しい課金なしで手に入る（案Aと同じgitの仕組み）。
- 遷移記録・確定入力・台帳の写しを、公開せずに保存できる。
- 台帳を同じ非公開リポジトリに置けば（U-11）、台帳の版をコミットSHAで参照でき、台帳の変更・消失もgitの履歴から追える。状態の参照（ランナーが書く）と台帳の参照（ユーザーが書く）を別にすれば、互いの書込みが比較交換で衝突しない。

案Bの条件とリスク：

- ユーザーが非公開リポジトリを作る必要がある（このセッションからは作れない）。
- Actions（公開リポジトリ側）から非公開リポジトリへ書くには、そのリポジトリだけに範囲を絞った書込み用の資格情報を、秘密として登録する必要がある。秘密の登録・workflow変更は別承認。ランナーをどちらのリポジトリで動かすかも未決（U-13）。
- 資格情報の漏えいは、状態の改ざんにつながる。範囲を1リポジトリ・必要な権限に限り、強制pushと削除を禁止するブランチ保護をかける案を、実装時に一緒に出す。
- **履歴の書き換えはしない**：強制pushは使わない。復旧も新しいコミットを足す形でだけ行う（案Aと同じ）。

案Aを選ぶ場合に公開される内容：対象D、armed、連続数、前日normal_raw、判定入力の値（公開市場データ）、decisionの値・観測時刻・record_id、実行区分。口座値・Webhook URL・認証値・`source_url`は入れない。

### 3.4 1回の実行の手順（案）

1. **ロック**：Actionsの`concurrency`（同じグループ、実行中を取り消さない）で、同時に走る実行を1つにする。ただし、これは補助で、正しさは手順5と手順7の比較交換で担保する。
2. **読込**：状態の参照の先頭を取得し、そのコミットSHAを「読んだ先頭」として覚える。参照が無い、`state.json`が無い場合は`state_missing`で止める（自動で初期状態を作らない、§4 E-12）。
3. **検査**：I-01〜I-11、IB-01〜IB-04、I-14、I-15。違反なら止める。
4. **追いつき（消費）**：§2.7の手順でコアへ渡す観測集合を作り、§2.8の開始位置（`as_of_d`があればその次。無ければ、さかのぼって最初に見つかるGENESISの`start_after`かRESTART_UNKNOWNの`resume_after`の次）から最新の確定セッションまで、古い順にコアを呼ぶ。
   - decisionがあるセッション：消費する。遷移記録1件（確定入力つき）と新しい`state.json`を1コミットにまとめ、手順5で保存してから次のセッションへ進む。
   - decisionが無く、そのセッションの観測窓（次の開場時刻まで）が閉じているセッション：何も保存しない。次に消費するセッションで、コアが欠測として扱う（遷移記録の`gap=true`、`skipped_sessions`にそのセッション）。
   - 最新のセッションでdecisionがまだ無い：消費しない（「F&G観測待ち」）。
   - コアが入力エラー・衝突を返したら、そのセッションで止める。それより後のセッションは処理しない。
5. **保存（比較交換）**：新しいコミットの親を「読んだ先頭」にし、早送りのpushで状態の参照を更新する。拒否されたら、他の実行が先に書いたということなので、§3.7の手順で読み直す。成否が分からなければ§3.8の手順で確かめる。成功したら「読んだ先頭」を新しいコミットにして手順4へ戻る。
6. **最新Dの評価**：消費後の状態で、最新の確定セッションを評価する（多くの日は「F&G観測待ち」で状態は変わらない）。
7. **送信権を取る**：§5.3の手順で`outbox/<D>-morning.claim.json`を新規作成し、比較交換で保存する。自分の`claim_id`が保存されたときだけ送信権を持つ。既に同じ鍵の意図があれば、内容が同じでも送らない。
8. **送信**（後工程のアダプタ）。送信権を持つ実行だけ。
9. **送信結果を記録**：`outbox/<D>-morning.result.json`を新規作成（`claim_id`つき）。「送った」「送っていないと確定」「不明」のどれか。

ユーザーがDの観測を朝の実行より後に記録するのが普通の流れなので、**Dの消費は、多くの場合、翌朝の実行（D+1の評価の前）で行われる**。夕方に消費だけを行う実行を足すかどうかは未決（U-09）。

### 3.5 原子的な保存

- **案A・B**：1回の遷移の内容（遷移記録と現在状態）は1つのコミットに入り、参照の更新は1回の早送りで成否が決まる。途中まで書かれた状態は外から見えない。R-2の復元は、RECOVERY_RESTOREと消費し直しのAPPLYと新しい`state.json`を1コミットにまとめる（§4.3）。
- **案F（ローカル）**：同じフォルダに一時ファイルを書き、`flush`と`fsync`の後で`os.replace`で置き換える（同じボリューム内。POSIXではさらにフォルダを`fsync`）。遷移記録は新しいファイルとして先に書き、現在状態の置換を最後にする。読込時に、遷移記録の最後の1件と現在状態の通番が合わなければ（置換の前に止まった場合）、止めて知らせる（自動で前に進めない）。通知の意図は排他的な新規作成（`O_CREAT|O_EXCL`）で作る。Windowsでは、同期フォルダ（OneDrive等）やウイルス対策ソフトがファイルを掴んで置換が失敗することがあるので、同期されないフォルダを使う。電源断に対する厳密な保証は、ファイルシステムの実装に依存する。

### 3.6 ロックと並行実行

| 層 | 仕組み | 役割 |
|---|---|---|
| 1 | Actionsの`concurrency`グループ（実行中を取り消さない） | 通常は同時に1つだけ走らせる。待機中の実行が新しい実行に置き換わることがあるので、取りこぼしは翌日の追いつきで回収する |
| 2 | 早送りだけの参照更新（比較交換） | 正しさの担保。層1を回避した実行（手動・ローカル）が同時に書いても、片方は拒否される |
| 3 | 通知の意図は新規作成だけ（§5.3） | 送信権を1つの実行に限る |
| 4 | ローカル実行は既定で読取専用 | PCでの試行は、明示的な指定が無い限り本番の保存先へ書かない |

期限つきのロック（リース）は使わない。期限切れのロックを自動で奪うと、遅い実行と新しい実行が両方書く事故が起きるため。案Fのロックファイルが残っていた場合も、自動では消さず、知らせて止める。

### 3.7 同日再実行と二重消費の防止

消費の鍵は「対象D」。有効な履歴の中で、遷移記録はDごとに1件までで、連続数やarmedが変わるのは遷移記録を1件足したときだけ。

| 状況 | 動き | 結果 |
|---|---|---|
| Dを消費済みで、同じ朝にもう一度実行 | 先頭の`as_of_d==D`。コアは基点から再計算（再実行の経路）。Dのdecisionは遷移記録の確定入力と台帳の突き合わせ（§2.7）を経て渡す | 再計算した状態・判定入力が保存値と一致すれば何も足さない（`state_updated=False`）。違えば止める（E-10） |
| 保存の前に止まった実行を、後でやり直す | 先頭は消費前のまま | 同じ基点から最初からやり直し、1回だけ消費する |
| 二つの実行が同じDを同時に消費 | 片方の早送りが拒否される | 拒否された側は読み直し、**有効な履歴に**同じDの遷移記録があり、内容（decisionの指紋・次状態の指紋・判定入力の指紋）が一致すれば成功扱いで何も足さない。違えば`concurrent_conflict`で止める（先頭の記録だけでなく、有効な履歴全体で探す。§3.8の「同じ内容」の判定と同じ） |
| 通知が失敗した後の再実行 | 状態は消費済み | 同じDを二度消費しない（1行目と同じ）。通知はoutboxの記録で判断（§5） |
| 復元の後で同じDを消費し直す | 古い記録は退避済み | 有効な履歴に1件だけ足す。退避した記録との差は計画で示す（§2.6、§4.3 R-2） |

「同じ内容なら成功扱い」は、外部への副作用が無い**状態の遷移だけ**に使う。通知の送信には使わない（§5.3）。

### 3.8 保存の成否が不明なときの確認（第4版で新設）

pushの応答が来ないなど、保存の成否が分からないときは、状態の参照の先頭を読み直し、次の順で判定する。初版〜第3版のE-03の「先頭が新しいコミットなら保存済み」は、他の実行による更新と区別できないので使わない。

| 順 | 確かめること | 判定 | 次の動き |
|---|---|---|---|
| 1 | 読み直しができたか | できない | 止める（終了1）。保存済みとも未保存とも書かない |
| 2 | **自分が作ったコミット**（そのSHA）が、新しい先頭から到達できるか（先頭そのもの、または先頭の祖先） | 到達できる | 自分の保存は確定。その後に他の実行が更新を進めていてもよい。ただし、自分の遷移記録がその後のRECOVERY_RESTOREで退避されていれば、「保存されたが退避済み」と報告し、消費し直さない |
| 3 | 到達できないとき、**有効な履歴に、自分が保存しようとしたのと同じDの遷移記録**があるか | あり、内容（decisionの指紋・判定入力の指紋・`state_after`の指紋）が一致 | 他の実行が同じ遷移を保存した。成功扱いで何も足さない |
| 4 | 同上 | あり、内容が違う | `concurrent_conflict`で止める。自分の内容では保存し直さない |
| 5 | 同上 | 無い | 未保存。新しい先頭から読み直して、追いつきを最初からやり直す（再試行の回数上限つき、U-12）。先頭が進んでいれば、その内容を前提に計算し直す |

- 判定2はコミットのSHAで行う。コミットのSHAには親と内容と時刻が入るので、他の実行のコミットと取り違えない。
- 判定3・4の「同じD」は、退避した履歴ではなく、有効な履歴の中で探す。
- 通知の意図（§5.3）も同じ考え方で、自分の`claim_id`が保存されたかを確かめる（意図のファイルの中身で判定する）。
- 案F（ローカル）では、自分が書いた遷移記録ファイルの指紋と、`state.json`が指す先頭の指紋で、同じ判定を行う。

## 4. 障害時の扱い

### 4.1 基本方針

- 迷ったら止める。止めるときは終了コード1、状態は変えない、市場判定の通知は出さず（または「判定を止めた」とだけ出す、U-08）、止めた理由のコードを出す。
- **黙って初期化しない**：状態が無い・壊れているときに、初期状態（UNKNOWN開始）を自動で作らない。初期化はユーザーの明示操作（§4.3 R-4）だけ。
- **黙って巻き戻さない**：古い遷移記録へ戻す、遷移記録を消す・書き換える、強制pushする、を自動で行わない。復旧は、新しい遷移記録を足す形でだけ行い、どの記録が有効でなくなったかを名指しする（§2.6）。
- **生の台帳を書き換えない**：ランナーは台帳を読むだけ。使わない観測は、指紋にひも付けた除外で扱う（§2.7）。
- 既存の「データ異常を条件未達にしない」方針（補正版A9）を、保存の障害にも適用する。保存できなかったことを「合図なし」と表示しない。

### 4.2 障害の一覧

| ID | 状況 | 検出 | その場の扱い | 復旧・再実行 |
|---|---|---|---|---|
| E-01 | 読込・計算中の中断 | — | 何も保存されていない | 次の実行で最初からやり直す |
| E-02 | コミットを作った後、pushの前に中断 | — | リモートは変わっていない | 同上。ローカルのコミットは捨てる |
| E-03 | pushの応答が来ない（成否不明） | タイムアウト等 | §3.8の手順で、自分のコミットが先頭から到達できるか、同じ内容の遷移が有効な履歴にあるかを確かめる。読み直せなければ止める（推測しない） | 保存済み（自分または同じ内容）なら次へ、内容の違う遷移があれば止める、未保存なら読み直してやり直す（回数上限つき、U-12） |
| E-04 | pushが早送りでないとして拒否 | 拒否応答 | §3.7の手順で読み直し | 状態の遷移は同じ内容なら成功扱い、違えば止める。通知の意図は§5.3 |
| E-05 | 保存の認証失敗・ネットワーク失敗が続く | 再試行の上限 | 止める。市場判定の通知は出さない（U-08） | 原因を直して再実行。状態は消費前のままなので二重消費しない |

## 5. 後段処理との境界

### 5.1 分離の原則

- 市場状態の更新（消費）は、通知・Sheetsの成否を根拠にしない。消費の保存は、通知を送る前に終える。
- 通知・Sheetsの失敗で、消費を取り消したり巻き戻したりしない。
- 後段が失敗して再実行しても、同じDを二度消費しない（§3.7）。
- 通知の記録（outbox）と状態の遷移記録は別のファイルにし、片方の破損がもう片方の検査を妨げないようにする。
- 復元（R-2）や消費し直しは、過去のDの通知を作らない。

### 5.2 通知の記録（outbox）

| 状態 | 意味 | 次の実行での扱い |
|---|---|---|
| 意図だけ（CLAIMED） | 送信権を取った記録（本文の指紋、宛先の種別。宛先URLは書かない） | 結果が無いまま残っていれば UNKNOWN とみなす |
| SENT | 送信先が受領を返した | 送らない |
| NOT_SENT | 送っていないと確定できる失敗（例：接続を始める前の失敗） | 自動再送の可否はU-04（推奨は、送信権を持つ同じ実行の中だけ、回数上限つき） |
| UNKNOWN | 送ったかどうか分からない（タイムアウト、応答なし、意図だけ残っている） | **自動で再送しない**。ユーザーの明示操作でだけ再送 |

鍵は「対象Dと通知の種別（朝の通知など）」。どの失敗が「送っていないと確定」に当たるかは送信先とアダプタによるので、アダプタを作るときに決める（U-04）。通知アダプタ自体は今回作らない。

### 5.3 送信権（第2版で新設）

初版の「同じ内容なら成功扱い」を通知の意図に当てはめると、同時に走った二つの実行が同じ意図を作り、どちらも「保存できた」と判断して両方が送り得る。第2版では、**送信できる実行を1つに限る契約**を置く。

1. **意図は新規作成だけ**：各実行は、実行ごとに一意な`claim_id`（実行IDと乱数）を含む`outbox/<D>-<種別>.claim.json`を、そのパスが先頭に**存在しないこと**を前提に作り、比較交換で保存する。既に存在するパスは上書きしない。
2. **送信権の判定**：自分の`claim_id`を含む意図が保存先に保存されたことを確かめた実行だけが送信権を持つ。
   - pushが成功した：送信権あり。
   - pushが拒否された：読み直す。そのパスに他の`claim_id`の意図があれば、本文の指紋が同じでも**送らない**（「他の実行が送信担当」として終了コード0）。意図が無ければ、新しい先頭の上で手順1をやり直す。
   - pushの成否が不明：読み直す。自分の`claim_id`があれば送信権あり、他の`claim_id`があれば送らない、意図が無ければ手順1をやり直す。読み直せなければ送らない。
3. **結果は送信権を持つ実行だけが書く**：`outbox/<D>-<種別>.result.json`を新規作成し、意図と同じ`claim_id`を書く。`claim_id`が合わない結果は無効（E-20）。
4. **意図はあるが結果が無い**：送信前に止まったのか送信後に止まったのか区別できないので、UNKNOWNとして扱い、自動で再送しない。
5. **手動の再送**（第3版で改めた）：第2版の`resend-<n>`は採番だけで、同じ再送依頼が二度実行されると、負けた側が次の番号で送り直し得た。第3版では次の契約にする。
   - **依頼の識別子**：再送はユーザーの明示操作（手動起動の入力やローカルのコマンド）で、`resend_request_id`を指定して依頼する。識別子は依頼の入力に含め、実行側では生成しない。同じ依頼をもう一度実行したとき（Actionsの再実行を含む）に、同じ識別子になるようにするため。文字種は§2.5と同じ。
   - **保存先は識別子で1つに決まる**：`outbox/<D>-<種別>.resend-<resend_request_id>.claim.json`。番号を振らない。
   - **新規作成だけ**：手順1〜4と同じく、そのパスが無いことを前提に作り、比較交換で保存する。自分の`claim_id`が保存された実行だけが送る。
   - **競合した側は送り直さない**：pushが拒否されて、そのパスに他の`claim_id`の意図があれば送らずに終わる（E-21）。別の番号や別のパスを作って送り直さない。同じ依頼を後でもう一度実行しても、意図が既にあるので送らない。
   - **再送できる条件**：元の意図の結果がUNKNOWNかNOT_SENTのときだけ。SENTの通知の再送依頼は受け付けない。再送の意図には`resend_of`（元の意図の`claim_id`）を書く。
   - **再送の再送**：再送がUNKNOWNになっても自動では送らない。もう一度送るには、ユーザーが新しい識別子で新しい依頼を出す。

状態の遷移では「同じ内容なら成功扱い」を続けて使う（副作用が無いので、どちらが保存しても結果は同じ）。通知では使わない。

### 5.4 Sheets

Sheetsへの記録も後段として同じ扱い：状態の根拠にしない、失敗で巻き戻さない、結果が不明なら自動で重ねて書かない。書く実行を1つに限る契約（§5.3と同じ形）を置く。Sheetsを状態の写し（人が読む表）にする場合も、正本は保存先（案Bなら非公開リポジトリ）とする。
