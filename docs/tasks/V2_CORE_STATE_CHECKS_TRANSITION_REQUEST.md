## 2. 作るもの

### 2.1 P-04：現在状態と基点を分けた読込検査

`MarketState.from_dict`（保存した状態を読む入口）で、最上位の状態と入れ子の基点に**別の規則**を当てる。設計案第4版§2.4のとおり。

現在状態（最上位だけ）：

| ID | 条件 |
|---|---|
| I-01 | `as_of_d`が無い ⇔ `fixed_decision`が無い ⇔ `base`が無い |
| I-02 | `as_of_d`が無いなら、armed=UNKNOWN、連続数0、前日normal_raw=UNKNOWN |
| I-03 | `fixed_decision.d == as_of_d` |
| I-04 | `base.as_of_d`は無いか、`as_of_d`より前 |
| I-05 | 連続数≥3ならarmed=TRUE |
| I-06 | 連続数≥1なら前日normal_raw=FALSE |
| I-07 | `fixed_decision.fingerprint`は小文字16進64桁、`fixed_decision.record_id`は§2.2の文字種 |

基点（`base`だけ）：

| ID | 条件 |
|---|---|
| IB-01 | `fixed_decision`と`base`を持たない（値がnullまたはキーが無い）。`as_of_d`はあってよい |
| IB-02 | `as_of_d`が無いなら、armed=UNKNOWN、連続数0、前日normal_raw=UNKNOWN |
| IB-03 | 連続数≥3ならarmed=TRUE、連続数≥1なら前日normal_raw=FALSE |

- 違反は既存と同じ`state_invalid`（入力エラー、終了コード1、値は表示しない）。どの規則に反したかは、値を含まない形で区別できるとよい（例：内部の理由コード。表示の文言は既存のまま）。
- **最上位の規則を基点に当てない**（設計案第2版で指摘された誤り）。今の`from_dict`は入れ子を同じ関数で読むので、最上位用と入れ子用を明示的に分けること。
- 検査は**読込の入口（`from_dict`）だけ**に置く。`MarketState`のコンストラクタや`evaluate_day`の引数には置かない。理由は2つ。
  - `MarketState`は現在状態と基点の両方に使うので、コンストラクタに最上位の規則を一律に当ててはいけない（基点を拒否してしまう）。
  - 既存の試験は、検査を通らない形の状態（`as_of_d`ありで`fixed_decision`・`base`なし等）を直接作って入力に使っており、それを変えないため。
- **直接構築した`MarketState`は、信頼済みの内部入力として扱う。** `from_dict`の検査は、永続化した状態を読むときの検証であり、直接構築した値が永続化可能な正しい状態であることは保証しない。この契約を、`state.py`の文書文字列（docstring）と結果文書に明記する。
- IB-04、I-08〜I-15（遷移記録が要る検査）は対象外（ランナー側）。

### 2.2 P-06：record_idの文字種

- 規則：`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`（英数字で始まり、英数字・ピリオド・下線・ハイフン、最大64文字）。`fullmatch`で判定する（末尾の改行を通さない。R-04と同じ注意）。
- 検査する場所：観測の解析（`parse_observation`、違反は既存の`record_id_invalid`）と、状態の読込（`fixed_decision.record_id`、違反は`state_invalid`）。
- エラー文・出力に、record_idの値を出さない（既存のA11の方針）。
- 実観測は0件なので、既存データの移行は無い。

### 2.3 U-14：純粋な遷移関数

通常の判定（`evaluate_day`）と、保存した入力からの再計算が、**同じ遷移計算**を使う構成にする。

- 新しい関数（名前・置き場所は案）：

```python
def apply_transition(base: MarketState, d: str, prev_session_date: str,
                     row: MarketRow, prev_row: Optional[MarketRow],
                     decision: Optional[Observation]) -> Transition
```

  - 入力は値だけ。市場系列・セッション列・観測の一覧・時計・ファイルを受け取らない。入出力・例外以外の副作用なし。
  - `Transition`は、今の`evaluate_day`の中で計算している次のものを返す：3条件の`RuleResult`（状態・比率・理由・`may_be_unconfirmed`）、実行区分、欠測の有無（`gap`）、判定に使った開始時のarmed・連続数・前日normal_raw、注記（`session_gap_state_degraded`、`fg_not_recorded`）、**次状態の候補**（decisionがあるときは基点にDを適用した状態、無いときは候補なし）。
  - **`state_updated`は返さない。** 引数には同じDの再実行かどうかの情報が無く、同じ基点・同じ入力から「新規の適用」と「再実行」は区別できないため。
  - 欠測の判定は、今と同じく`base.as_of_d`が無いか`prev_session_date`と同じかで行う。前日の市場側normalは`prev_row`から計算し、`prev_row`が無ければ今と同じく「不明」として扱う。
- `evaluate_day`の責務は、入力の検査、Dで切った系列からの行の取り出し、decisionの選択、同じDの再実行の判定と基点の選択、未処理の中間セッションの検査（R-02）、表示用の項目（セッション時刻、待機S、SOXL終値、系列のメタデータ）に限り、遷移の計算は`apply_transition`を呼ぶだけにする。遷移の計算を2か所に持たない。
- **`evaluate_day`側で確定するもの**：最終の次状態と`state_updated`。
  - 次状態：decisionがあれば`apply_transition`の候補、無ければ今と同じく入力の状態をそのまま返す。
  - `state_updated`：decisionがあり、かつ同じDの再実行でないときだけtrue。decisionが無いとき、同じDの再実行のときはfalse。今の動作と同じ。
- `ErrorResult`への変換（`run_day_safe`）、表示・プレビューの出力は変えない。
- 設計案§2.3が保存する`rule_inputs`（D行と前日行の値）と`decision_record`から`apply_transition`を呼べば、同じ次状態・判定が得られることを試験で示す（§3のA-04）。保存の形式そのもの（遷移記録のJSON）は作らない。

A-03の内容（第2版で範囲を改めた）：

- 正常な基点を受け付ける：`as_of_d`あり・`fixed_decision`なし・`base`なしの基点を持つ状態（設計案K-07）、基点が初期状態の状態（K-09）、既存試験の`GOOD`と同じ形の状態。
- 往復（`to_dict()`→`from_dict()`で元と一致）を求めるのは、**永続化可能な正常状態から始めたケース**だけ：
  - 初期状態から始め、合成のF&G列（観測なしの日・欠測・同じDの再実行を含む）を順に処理した各段階の状態。

- 往復を求めないもの：
  - 直接構築した不完全な状態から始めたケース。decisionが無い日は入力の状態がそのまま返るので、不完全なまま出てくる（例：A1の通し計算は、2024-10-01の状態を直接構築して始めるので、A-03の対象にしない。A-04の比較には使う）。

- 不正な保存状態の拒否はA-02で確かめ、往復の試験とは分ける。

A-04の内容（抽出前後の動作比較。保存状態として正しいかどうかとは独立に、同じ入力に同じ出力を返すことだけを見る）：

- **(a) 抽出前の動作との一致**：コードを変える前に、`1a54a85`のコードで、決めた入力の集合を評価した結果（`DayResult`の全項目、または`ErrorResult`のコード・項目・詳細・終了コード）をJSONとして保存する。生成に使ったスクリプトと、生成時のSHA（`1a54a85`）を一緒にコミットする。抽出後のコードで同じ入力を評価し、全件が一致すること。
  - この基準データは**抽出前の製品コードの出力**で、正しさの基準ではない。リファクタの前後で動作が変わっていないことだけを示す。正しさの試験（A1・A3〜A5等）の期待値は、従来どおり製品の関数から作らない。
  - 入力の集合は少なくとも次を含む：A1の研究fixtureでの465日の通し計算（既存の試験と同じ入力と初期状態）。合成の格子（格子の状態は直接構築した内部入力で、保存状態としての正しさは問わない。基点のarmed 3値×連続数{0,1,2,3}×前日normal_raw 3値のうちI-05・I-06を満たす組、基点の`as_of_d`{無し、前のセッション、2つ以上前（欠測）}、F&G{観測なし、0、24.99、25、27.5、29.99、30、30.01、100}、市場側{normal成立、trend成立、どちらも不成立}×前日の市場側normal{成立、不成立}）。同じDの再実行（一致・衝突）、未処理の中間セッション、decision衝突、データ異常の代表例。
- **(b) 保存入力からの再計算との一致**：(a)の各ケースでdecisionがあるものについて、`evaluate_day`が使った基点・D行・前日行・decisionを値として取り出し、`apply_transition`を直接呼んだ結果（次状態の候補・判定）が、`evaluate_day`の次状態・判定と一致すること。同じDの再実行のケースでも候補は同じで、`state_updated`だけがfalseになることを確かめる。
