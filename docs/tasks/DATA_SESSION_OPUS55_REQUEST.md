## 成果：採否判断ができる1つの仕様案

保存想定：`docs/specs/DATA_SESSION_CONTRACT_DRAFT.md`。
内容は価格・対象日の2設計を中心に150〜250行程度を目安とし、必要なら増減可。コード・設定の変更、試験実行、送信は依頼していない。保存権限がなければMarkdown全文を返し、未保存を明記する。

### A. 価格と依存の契約
- 試験済みの直接依存版を固定する方向を具体化し、推移依存・Python／OS・新規カレンダー依存の再現性の限界を示す。まだ固定コードを作らない。
- SOXXのSMA／RSI、SPY/IEFのSHDに使う系列と、SOXLの表示／Sheets価格、将来の損益台帳を分けて定義する。
- auto_adjust=True明示で現候補を比較基準にする案と、auto_adjust=FalseでClose/Adj Close等を保持して用途別に選ぶ案を比較し、**推奨1案**を示す。単に全てFalseにする結論にしない。Closeを完全無調整・当時の約定と呼ばない。
- 分配金・分割・後日の履歴改訂、取得時点、将来情報の混入、欠落時の停止、価格系列の取り違えを扱う。指標への調整価格利用と、損益／分配金の二重計上を区別する。
- 現在のyfinance既定を、旧Actions環境や第三者研究データの価格定義だったと推測しない。既存データ・利益額の上書きや戦略の採用をしない。
- 決定前に必要なデータ／比較、未取得で保留する結論を明示する。

### B. 独立した対象セッション決定
- カレンダー候補と公式根拠、有効範囲・期限切れ、America/New_York／UTC／JST、実実行時刻、取得範囲を具体化する。
- 「予定されていた日」と実起動時刻から決めた日をどう区別するか。予定時刻を取得できない場合、取得済みと仮定しない。
- 通常日・休場・短縮取引・夏冬時間・週末・遅延・NY日付跨ぎ・手動再実行を例示。市場終了と上流データ到着／確定を分ける。必要なら待機猶予を提案し、未検証を明示する。
- データ最終日、JSTの前日、単純な平日計算、古い共通有効日へ落とす処理を代用しない。
- 対象日の元価格と、指標に必要な履歴セッションの連続性をどこで検査するかを示す。行が丸ごと抜けた場合も考慮する。
- 休場の正常スキップ、時刻尚早、カレンダー不明、データ異常、明示的な再現を区別する擬似コード・状態／終了表を作る。
- 完了サマリは実行ごとに出す採用事項を維持。再実行の報告とSheets価格行の重複を分け、最小の扱いを提案する。保有・約定台帳や自動発注は追加しない。
- 未起動を内部から検知できると説明しない。JSTの確認期限は具体案1つと根拠・限界を示してよいが未採用。新監視・有料サービスは導入しない。
