## 3. 設計で具体化すること

S3第3版§9を前提に、少なくとも次を一つの矛盾のない契約へまとめる。

- **新形式と移行**：schema=1と新形式を区別する全キー・型・hash計算・コア互換。旧Snapshotの原本保全、明示変換、元のseq/hashとの対応、S3-A ResolutionSetの指紋・名前空間・request_idを新履歴へ写す規則。S3-Aは永続化済みの証拠ではないため、持ち込む記録の確認根拠と完全な候補の再検査を省略しない。旧S1／S2検査器を緩めたり、状態とResolutionSetを別々に更新したりしない。
- **監査履歴と有効履歴**：全履歴の直前親と有効親、0基点の連続seq、単調な新規採番、現在状態を作ったAPPLYとその親state_afterを使うbase検査。ACK／宣言は市場状態・開始境界を動かさない。退避された履歴も保全する。
- **復元計画**：復元先は現在有効な検証済み記録だけ。supersededは復元先以後から旧有効先頭までの有効記録をちょうど列挙する。物理seqの単純区間で古い退避記録を巻き込まない。複数回の復元、途中に制御記録がある例、退避済みノードへの再接続拒否を示す。
- **制御記録と再計算**：ACK／DECLARE_MISSING／RESTART_UNKNOWNを黙って落とさず、再生対象・参照写像・無効となる条件を明記。元の指紋と現在台帳の違い、市場入力やセッション文脈の差を検査し、CORRECTIONや未処理の版の選択を復元で迂回しない。通常計算は既存evaluate_day、保存入力の再計算はapply_transitionへ委譲し、戦略式を複製しない。
- **一括公開の境界**：計画hash・全入力digest・期待先頭に結び付け、復元記録・再計算したAPPLY群・解決記録・次状態を一括で比較更新する契約。復元途中の状態を先に公開しない。既存単一AppendPlanが新バッチを受けられない点と、S2の既存公開APIを変更せず実現できる範囲／別アダプタが必要な範囲を分ける。
- **UNKNOWN再開始**：resume_afterは最後のAPPLY、宣言済み日、直近開始境界を下回らない。過去履歴を削除せず、ACK／宣言で開始位置を動かさない。同日再実行・欠測・後発行・UNKNOWN後の最初の処理を具体例で固定する。
- **破損診断**：検証可能なprefixの診断と、正本として採用できる完全候補を区別する。破損suffixを無視してvalidと返さない。元バイトと破損証拠の実保全・採用実行はS3-Cの責任範囲とつなぎ、Bだけで復旧済みと主張しない。

通知意図・手動再送・outbox・配信権は再構築しない。新保存先・資格情報・ライブ台帳・本番のU-01／U-11／U-13や保有情報は、この設計で採用したことにしない。S3-Cの実解錠・保守ゲート・退避先の同期・Windows strictを既に解決した前提で書かない。
