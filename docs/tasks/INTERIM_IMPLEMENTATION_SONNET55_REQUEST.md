## 3. 実装する最小単位

### A. データ検査を判定より前に置く
- 取得失敗、空データ、列・銘柄不足、日付不一致・順序異常、元価格の欠損／非有限／不正、履歴不足、指標の非有限を明示的に扱う。
- 正しい対象セッションを独立した入力／検証可能な方法で固定し、対象日と必要銘柄（SOXX/SOXL/SPY/IEF）の元価格を確認する。返ってきたデータの最新日が古いままでも通る検査にしない。
- 200SMA、RSI、SHDの計算に必要な履歴の妥当性を確認。SHDだけ古い共通有効日へ落ちたり、最新価格NaNでRSIが前日値を持ち越したりしても通さない。欠損の補完で誤魔化さない。
- 検査NGでは判定関数と通常のSheets価格行追記を実行せず、運用エラーの通知を試み、非0終了。
- 同日の全銘柄・列をそろえただけでは対象セッションの正しさを保証しない。カレンダー・確定時刻の自動決定に未解決点があれば、明示した対象日のオフライン検証まで進め、運用切替条件として報告する。
- yfinanceの列構造・調整価格等の既定値に依存する箇所は実際の依存版とともに記録。計算方式や調整有無を無断で変更しない。実データ取得は今回の試験に使わない。

### B. 毎回のサマリと失敗時の終了
- 既存の保有に依存しない技術条件だけを確認する（SOXX終値>200SMA、SHD<0、RSI<=55）。閾値を探索・変更しない。
- 正常な条件未達も1回のサマリで通知。対象日・検査・技術条件・Sheets結果・F&G目視未確認を区別する。技術条件成立でも購入推奨・購入可否確定としない。
- Sheets無効を明示した状態と必須設定不足を区別。有効時の書込失敗は部分失敗サマリの通知を試み、その成否によらず非0。
- HTTPの明示的失敗と、タイムアウト等による配信不明を区別。成功以外を成功ログにしない。非秘密のHTTPステータス・対象日は残し、Webhook URL・応答本文・生例外・認証情報は出さない。
- ネットワーク呼出しには有限のタイムアウトを設ける。自動再送を追加せず、配信不明の重複通知を避ける。通知失敗時に同じ通知関数へ再帰しない。
- 必須通知設定の欠落は通知無効という正常状態へ置き換えず非0。設定をログへ表示しない。
- import・取得・書込・送信の境界を分け、試験でネットワークを禁止し、呼出し回数と順序を確認できる構成にする。

### C. 売却系の抑止
- 売却推奨、全額売却、緊急脱出、旧過熱条件による参考通知は出さない。OFF案だけを実装し、未採用ON機能を追加しない。
- 保有・原価を読み込まない。未知の保有を0株とせず、初回参加／再エントリー分類・数量・配分も出さない。
- 通知を約定として記録せず、保有・原価・状態を更新しない。研究のRSI75・利確20%・2%ゲート等は混ぜない。

### D. pip等の失敗通知候補
- 通常サマリを出すアプリ本体の依存が入らなくても、利用可能な実行系から失敗報告を試みる候補を作る。新サービス・新しい秘密設定は追加しない。
- 元の失敗を通知成功で0へ変えず、通知失敗でも元の異常を残す。アプリが通知を試みた後にYAML側が同じエラーを二重送信しないよう役割を分ける。
- checkoutやPython自体の準備失敗、Actions未起動、共通通知経路故障等はすべてを保証できない。可能な範囲と限界を明示する。
- YAML候補の構造・条件と報告関数をオフラインで確認する。実Actionsによるpip失敗試験や手動起動は行わない。
