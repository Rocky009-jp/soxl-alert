## 3. 実装する契約

設計書§4〜§9を仕様とする。依頼書は設計の範囲を狭めるためのもので、相反する新しい計算式を追加しない。実装上の矛盾があれば§6の手順を使う。

### 3.1 保存ドメイン

- Snapshot、GENESIS、APPLY、AppendPlanと結果の型を作る。スキーマはS1専用の版1。GENESIS.start_afterは明示された確認済みセッションの除外下限。boundary_session.dateと一致し、as_of_dはnullのまま、初回Dはその後。境界当日を適用・欠測として記録せず、自動推定や初期状態以外の取込みもしない。
- seq・親hash・event_hash・input_hash・Dの昇順・current_stateを検査し、履歴全体を保存入力から再計算する。
- 現在状態／state_afterの検査はMarketState.from_dict、基点の比較は親state_afterからfixed_decisionとbaseを落とした値に対して行う。正常な基点を現在状態の検査で拒否しない。
- confirmed_inputsは選択decision、D行、前日行またはnull、prev_session_date、必要範囲のsession_context。input_hashには、next(D)のclose_at／confirmedだけを除いた投影を使う。next(D)のdate／open_atは含める。保存する完全な写しとevent_hashには除外2項目も残す。投影をSessionListの入力にせず、同日比較で完全なsession_contextの直接一致も要求しない。無関係な台帳や市場の後日データはハッシュに含めない。
- 市場数値の型と範囲、日付、UTC時刻、窓、decision指紋を検査する。スキーマ外・重複JSONキー・非有限数値を拒否する。
- 通常計算はevaluate_day、保存入力からの再計算はapply_transitionを使う。条件式や状態更新式を新規パッケージへ複製しない。

### 3.2 単日ランナー

- 明示Dだけを処理する。snapshot検査、必要セッション確認、台帳照合、コア呼出の順を固定する。
- 台帳は境界以降を含む写し。適用済みdecisionの削除／変更／追加、欠測区間への遅着は停止する。ACKや補完で先へ進めない。
- 適用済み各Dの保存範囲を現在sessionsから切り出し、必要窓のどちらかが欠ければsession_context_missing、存在して保存投影と異なればsession_context_mismatch。投影は当該Dのnext(D)のclose_at／confirmedだけを除く。この照合は台帳選択より先なので、同じ最新Dのセッション相違にも先にこのcodeを使う。
- 新しいDを準備する際、通常・初回とも基準境界BとDの間の全セッションSにconfirmed=trueを求める。未確定があれば必要sessions検査でintermediate_session_unconfirmed（field=sessions）、計画なしで停止する。decision無しのSにも適用し、next(D)には適用しない。確定確認後、全Sへselect_decisionを日付順に適用する。窓外decision等は既存codeで確定前に拒否する。全Sの検査後に有効decisionがあればintermediate_session_unprocessed。first_unprocessed_sessionだけで済ませず、途中Dも自動処理しない。
- decision無しは計画なし。新規decisionは1件の準備だけ。作成したAPPLYを追記した候補Snapshotをvalidate_snapshotと同じ経路で全検査・再計算し、合格後にだけPREPAREDを返す。同じ最新Dで確定入力・遷移判定・状態が同じなら追記なし。判定が同じでも市場入力が違えばrecompute_mismatch。
- 台帳照合では、select_decisionの結果が無し、または正常に選択された単一行の指紋が保存値と違う場合にledger_mismatchとする。旧新併存・追加等でselect_decisionが出すrecord_id_conflict／decision_conflict／decision_outside_window等は、そのcodeを保持する。詳細は直後の対応表に従い、コア単体とラッパーの優先順位差を隠さない。
- 正常commit直後に他の更新を挟まず、同じseries・sessions・台帳で同じ最新Dを再実行すれば、必ずALREADY_APPLIED、計画なし・追加0件。core_result.state_updatedを保存成功の意味へ変更しない。COMMITTEDはcommit成功時だけ返す。
- エラーcode／field／優先順位は設計§9の対応表に従う。注入台帳への既存code保持と、保存Snapshot内部の不整合をsnapshot_invalidへ包む場合を区別する。

台帳のcodeは次の単独事象で固定する。構文が正しく、他の同時異常が無いケースの期待値であり、複数異常がある場合の順序は設計§9とselect_decisionに従う。

| 台帳の事象 | 期待code |
|---|---|
| 適用済みの元decision行を削除 | ledger_mismatch |
| 元decisionを別内容へ置換し旧行は残っていない | ledger_mismatch |
| 同じrecord_idの旧行と新内容の行が併存 | record_id_conflict |
| 元行を残し、同じDの窓内decisionを別IDで追加 | decision_conflict |
| 対象Dのdecisionが観測窓外 | decision_outside_window |
| 対象Sの窓内に別対象日のdecision | target_mismatch |
| 既存の欠測日に窓内の有効decisionが1件現れる | late_observation |
| 新規APPLYの中間日に窓内の有効decisionがある | intermediate_session_unprocessed |

### 3.3 MemoryStore

- 明示initializeのみ。未初期化を自動で初期状態へ置き換えない。initializeはGENESIS1件のみを受け付ける。
- 同一ロック内の先頭比較・全検査・1回の置換でcommitする。競合側は状態不変のcas_conflict。
- 読取・書込・計画の内側のdictやlistを外から変更できないようにする。
- 成否不明時はreconcileでDと親hash・確定入力・判定・状態を照合する。先頭が進んだだけで成功扱いしない。照合は書かず、競合後に古い計画を付け替えない。
- 同内容で他の実行が保存した場合のALREADY_APPLIEDは、自分の送信権を意味しない。通知のAPIを設けない。

A-06の競合は単なる逐次呼出だけで済ませない。Barrier等を用いて同じ先頭から準備した2スレッドを実行し、更新成功数とAPPLY件数を検査する。sleepによる偶然の競合待ちに依存しない。異なるDの計画では、双方を初期同一先頭から作れる台帳条件を明記する。
