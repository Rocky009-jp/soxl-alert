## 4. 6.1 Sol Highが提示する暫定方針

以下は **今回の仕様案で検討する前提**。ユーザー採用承認でも、正式な売買戦略の確定でもない。矛盾や不足があれば根拠と最小の論点を返し、独断で採用しない。

### A. 毎回の実行結果通知

- 正常な条件未達でも、対象取引日・データ検査・判定完了が分かるサマリを出す案とする。売買候補がある場合も、確認済みと未確認条件を区別する。
- データ欠損・日付不一致・履歴不足では売買判定を止め、運用エラーとする。数値のRSIが残っていても対象日の元価格が欠損なら有効としない。
- 異常時は通知成否にかかわらず非0終了する案。通知失敗を正常終了にしない。
- Sheetsが有効な構成で書き込み失敗した場合は、通知可能なら「記録失敗」を含む部分失敗サマリを出し、その後も非0終了する案。Sheetsで失敗しただけで通知まで黙って中止しない。任意連携が明示的に無効な場合と、必須設定の欠落を区別する。
- pip等の失敗でも報告を試みるため、アプリ本体の依存導入に依存しない報告処理を検討する。ただし具体コード・YAMLは書かない。
- ワークフロー未起動・実行基盤停止・通知経路故障は、内部の完了処理だけで自動検知できない。届かない場合は未確認とし、確認期限と必要なら独立監視を別の判断事項とする。新規サービス導入を既定案にしない。
- GitHubの失敗通知はユーザーが受信者・設定・到達を確認するまで未設定扱い。既知の情報から確認済みと推測しない。
- 再帰・無限再送・配信不明時の盲目的な再試行は入れない。結果通知と売買候補の重複防止・保有状態更新を分ける。売買候補の通知や技術参考情報を、約定として記録しない。

### B. 保有・費用込み原価の入力経路、責任、鮮度

暫定仕様案の出発点として、**ユーザーが確認した手動スナップショットを非公開の保存先から読み取る**方式を第一候補にする。既存の非公開Google Sheetsを拡張する候補を整理し、実際のタブ追加・権限変更・読み取りは行わない。新しい公開GitHubファイルや平文コミットを保管先にしない。証券口座API接続は追加しない。

必要項目の案：
- SOXL保有の確認有無、整数の株数、保有分の費用込み総取得原価USD。
- 参照元、実際の約定・入出庫等の最終変更時刻、ユーザー確認時刻、確認対象セッション。
- 未約定・部分約定・未反映イベントの有無。これらが不明なら状態未確認。

取得原価は保有分の購入費用込み総額とし、株価時価や円換算の表示値と混ぜない。平均原価は株数が正の場合だけ総額÷株数で求める。これは入力の定義案であり、未検証の税務計算や実口座台帳を自動生成する依頼ではない。

入力・確認・約定後更新の責任はユーザー。アプリは整合性・対象セッション・確認時刻を検査し、読込時刻をユーザー確認時刻と扱わない。通知だけで値を更新しない。

未入力を株数0と解釈しない。明示的に確認された株数0と、状態不明を分ける。最終変更がない長期保有を単に日数経過で損切り扱いにしない。一方、外部取引がなかったことも推測しない。売却可否を扱う場面では対象セッションに対するユーザー確認と、以後の未反映イベントの扱いが必要な案とする。具体的な確認頻度・有効期限は運用負担とともに未決事項として示す。

重要：保有入力が設計できても、執行価格・費用・注文不成立等の仕様が未確定な今回の暫定版では、**原価が有効なら売却を推奨できると結論づけない**。

### C. 参考情報と旧条件

R-02の暫定版は、保有・原価・費用・執行条件を確認する仕組みが整うまで売却推奨・全額売却・緊急脱出の案内を出さない。

参考情報を出すかはユーザーの未決事項。未承認時は出さない案を安全な初期案として示す。出す場合の仕様案では、旧条件 `RSI >= 70 OR SHD >= 3.0` を **技術参考情報専用の暫定条件** として分離して記載する。理由は既存挙動との対応を追えること。将来利益の優位性や、旧条件の正式採用を意味しない。

参考情報には、データ有効性・対象日一致の検査を必須とする。古いSHDで発火させず、売却可否は未判定と明示する。研究候補のRSI75・利益20%・2%ゲートを未承認で混ぜない。別の閾値探索や新しい利確ルールは提案範囲外。

### D. 現行運用

一時停止推奨は維持するが、停止／継続はユーザーの未決事項。仕様書を作成するために現行ワークフローを停止・起動・変更しない。

## 5. 成果物に必要な節

1. 目的、対象版、固定条件、案・未承認の表示。
2. 正常／異常／部分失敗／未起動・配信不明の状態表。通知内容と終了結果を分ける。
3. Sheets失敗時の順序、通知失敗時のログ・終了、重複防止と未起動検知の限界。
4. 保有スナップショットの項目定義、入力責任、鮮度と未知状態の扱い。
5. 参考情報の有無・旧条件・売却推奨との境界。
6. 受入ケース表：入力／期待通知／終了結果／状態更新の有無／確認方法。12件程度を上限の目安とする。
7. ユーザー承認5項目を1表にし、推奨案と未決を明示する。技術上の補足を新しい承認必須項目として際限なく増やさない。
8. 残る論点と、承認後に可能な最小実装単位。

受入表には少なくとも、正常な条件未達、目視F&G未確認、元価格欠損なのにRSI数値、日付不一致、Sheets失敗、HTTP失敗・配信不明、pip失敗、ワークフロー未起動、保有未入力と明示0、保有確認後の未反映約定、原価が有効でも執行条件不明、参考情報OFF／ONを含める。ケースをまとめてもよい。表の作成であり、試験実施済みと書かない。
