## 1. 調整価格の起源・欠落

auto_adjust=Falseで指標はAdj Close、SOXL表示はClose/Openという用途分離案を土台にする。yfinance内部がAdj CloseをCloseへ黙って代用する既知挙動に対し、どこで何を確認でき、何は確認できないかを仕様化。

Adj Close列の存在、配当イベント/比率のヒューリスティックだけで「非代用を証明」としない。欠落/起源未確認/異常の状態、指標計算やSheetsへの進行可否、終了・サマリを決める。必要なら元応答を厳格検査する案も比較するが、実取得や新規API実装はしない。検知できない事項を検知できる試験として設計しない。

## 2. RSI窓・価格方式変更の検証

同じ応答/同じ履歴窓ならTrueのCloseとFalseのAdj Closeが対応することと、period=1yからN=260へ変える影響を分ける。RSIの種/窓/必要履歴/対象日境界を一つの推奨へ固定する案を示す。

「窓を変えても完全同一」「55/75の閾値に将来一切影響しない」とはしない。受入確認は同窓の列対応と、窓変更の差を別に定義する。合成ケースの設計でよく、市場取得や追加グリッドは不要。新しい売買閾値を提案しない。

## 3. 対象日と遅延

T以前の直近cronからFを逆算する案は、24時間以上等の遅延を一般に識別できない。利用できる情報と限界を明記し、正常扱いする範囲を決める。

必要なら、対象Dを「実行開始T時点でカレンダー上確定したセッション」と定義し、元の予定日と混同しない代案も比較してよい。元の予定日が不明なのに取得済みとする方式、データ最終日/JST前日への代用は不可。取引時間中、確定待ち、休場、短縮、夏冬、次セッション以後、手動replayの状態を一貫させる。

GRACE60分は日足確定の保証ではない。期限切れカレンダーやデータ遅延は異常として扱い、古いデータで正常終了しない。

## 4. Sheets重複・競合・旧行

ワークフロー内の直列化等を提案する場合も、他クライアントの手動編集まで保証しない。列/タブ追加など既存シートを変える案は承認前の案にとどめる。Sheets無効/設定欠落/部分失敗の既存採用規則は変えない。
