# V2 朝の実行 手順書（非公開リポジトリでの運用）

版：S4-E の E-0（2026-11-05、日本時間）。対象：Rocky さん。公開リポジトリの `docs/ops/` に置く手順書で、秘密の値・Webhook の URL・口座の情報・手元のパスは書かない。

**この手順書の操作は、承認された段階でだけ行う。** E-0（コード）の受領は、非公開リポジトリの作成、workflow の追加、秘密の登録、試運転、実送信、本番の有効化のどれの承認でもない。E-1〜E-5 は、各段階の直前に別の承認を取る。公開リポジトリの main（31144d9）のジョブは停止のままで、どの段階でも変えない。

運用の前提は日足だけである。早朝に米国の確定日足で通知し、あなたが CNN の Fear & Greed の現在値を目視で台帳へ記録し、夜の寄付きで手動で購入する。自動発注・口座への接続は無い。

## 1. 毎朝の流れ

- 通知は、日本時間の **火〜土の 7:40（1回目）と 8:40（2回目）** に走る実行から届く（GitHub の定時の実行は混む時間に数分〜数十分遅れ、まれに飛ばされる）。通常は 7:40〜9:00 ごろに 1 通届く。
- 通知が無い朝：日曜・月曜の朝（米国は土日が休み）と、米国の休場日の翌朝。新しい対象日が無いので、2 回とも何も送らない（Actions の画面には「SKIPPED_CLAIMED」と出る）。
- **届くべき朝に 9:30 までに来なければ止まっている**と読む。Actions の画面（非公開リポジトリの Actions の `v2-morning`）で、その朝の実行と失敗を見る。
- 失敗のメール：実行が失敗（終了コード 1）すると、GitHub から「cron を最後に変えた人」にメールが届く。**cron の行を含むコミットは Rocky さん本人が行い**、GitHub の通知の設定（Settings の Notifications の Actions）で、失敗のメールを受け取る設定にする。メールが来ない設定のままでは「来なければ止まっている」の 2 つ目の知らせが無い。
- 終了コード 0 でも「判定なし」の通知が届くことがある（取得先の不調など。§7）。通知は届いているので失敗にはならない。

## 2. 台帳の書き方

- **F&G は 1 回目の実行（7:40）までに記録する。** 間に合わなければ、「F&G 未記録で購入条件は未確定」という分岐の文面が届き、2 回目（8:40）の実行でも再通知は無い（判定を出し直さない）。2 回目の実行は取得の失敗には効くが、記録の遅れには効かない。**遅れても次の寄付きの前までに必ず記録する。しないと欠測になる。**
- 台帳は、非公開リポジトリの `v2-ledger` ブランチの `observations.csv`。GitHub のウェブ（スマートフォンでも可）でファイルを開き、1 行足してコミットする。ランナーは台帳に書かない。
- 列（この順、1 行目の見出しはこのとおり）：

      record_id,target_us_session_date,observation_role,observation_status,current_fg_value,observed_at_iso8601

- 書き方の例（日付は例）：

      fg-2026-11-05,2026-11-05,decision,observed,23,2026-11-06T07:05+09:00
      fg-2026-11-06,2026-11-06,decision,not_checked,,

  - record_id は `fg-<対象日>` を勧める（補足の観測は `fg-<対象日>-s1` 等）。
  - 時刻は必ず **`+09:00` を付ける**（付けない・`+00:00` と書くと、今より後の観測として台帳の誤りで止まる）。引けの後、次の寄付きの前（日本時間の朝）に観測する。
  - **合図なしの日も decision を記録する。** 未確認の日は `not_checked`（値と時刻は空欄）。0 や前日の値で埋めない。
  - **古い行を消さない・書き換えない。** 保存した日の decision が台帳から消える・変わると、`ledger_mismatch` で止まる。
- **台帳の始め方**（E-2）：非公開リポジトリのウェブで `v2-ledger` のブランチを作り、見出しの 1 行だけの `observations.csv` を置く。見出しだけの台帳は読込みを通る。台帳は試運転（dry）と本番（live）で同じ 1 つで、E-2 から E-5 まで毎日続けて記録する（§12）。

## 3. 通知の読み方

- **判定あり**（鍵 `<D>-morning`）：その日の合図と確認事項。
- **判定なし**（鍵 `<D>-halt`）：「今朝は結果を出していません。条件未達ではありません」。理由コードが付く。前日の値で補っていない。
- **実行の誤り**（鍵 `<日付>-error`）：入口が日を決められないとき（表の終わりを過ぎた等）の 1 通。
- 同じ対象日の判定なしの後に判定ありが届いたら、**判定ありが有効**（同じ朝の 2 回目で取得に成功した場合など）。
- 実際に届く文面の見出しは「【詳細】」。中身はコアの文面で、送る直前に見出しだけ置き換えている。
- 判定なしのときも、売買の推奨は無い。購入は、判定ありの文面と、あなたが見た F&G の現在値で、あなたが決める。

## 4. 手動の操作

- Actions の `v2-morning` の「Run workflow」で、入力を選んで走らせる。
  - `command`：`morning` / `status` / `resend` / `init` / `check-source`。
  - `mode`：`auto`（既定）・`dry`・`live`。`auto` は workflow の `V2_MODE` に従う（定時の実行と同じ値）。
  - `date`（status・resend）、`kind`（resend：morning / halt / error）、`request_id`（resend：毎回新しい値）、`start_after`（init）。
- **本番（E-5）の後の手動の操作は、`mode` を `auto` のままにする（または `live`）。`dry` を選ぶと送信されない。** `dry` で手動の `morning` を走らせると、終了コード 0 で、何も送られないまま終わる。
- 手動の `morning` を日本時間 9:00 より後に走らせると、実行の誤りの予備の鍵の日付が対象日の翌日になり、判定ありが届いていても「実行の誤り」の通知が届くことがある。**その日の判定ありが届いていれば、判定ありが有効。**
- 読むだけの `status`・`check-source` は、書く実行（定時・手動の `morning`・`resend`・`init`）と別のグループで走り、待たせない。待ちの実行を取り消さないための分け方である（`queue: max` が使えない場合は「待ちの実行があるときは手動の実行をしない」）。
- 実行の記録（Actions の要約）には、コード・日付・hash（先頭 12 桁）・数・秒だけが書かれる。パス・URL・秘密・例外の本文は書かれない。

## 5. 再送

- `NOT_SENT`（送っていない）・`UNKNOWN`（届いたか分からない）の朝は、まず `status`（`date` を指定）で状態を確かめる。
- 送り直すときは `resend`（`date`・`kind`・新しい `request_id`）。同じ `request_id` は 2 度送られない。元が `SENT` の鍵は再送されない。
- **HALT・ERROR の再送は、同じ日の判定あり（morning の鍵）が `NONE` 以外なら、入口が断る**（`REFUSED_JUDGMENT_EXISTS`）。判定ありを待つ。
- 文面の先頭に「【再送】」の行が付く。Discord が 5xx・時間切れを返しても実際には投稿されていることがあり、再送すると同じ文面が 2 つ届き得る。
- **CLAIM_FAILED**（送信権を作れなかった。送っていない）：`status` で同じ鍵を確かめ、`NONE` なら同じ朝に `morning` をもう一度、再送なら新しい `request_id` で `resend` をもう一度。

## 6. DAMAGED

- `status` に `DAMAGED` と出たら、まず**時間を置いてもう一度 `status`** を見る（一時的な読めなさか、壊れたファイルかを見分ける）。続くなら壊れている。
- **壊れたままのときは止めて、Claude に相談する。手で直さない**（`v2-outbox`・`v2-state` を手で書き換えない）。

## 7. 止まり続ける理由コード

「判定なし」の文面の理由コードごとの扱い：

| コード | 意味 | 扱い |
|---|---|---|
| `input_market_fetch_failed` | 取得先の不調 | 次の朝を待つ。続けば相談（§13 の語を見る） |
| `input_market_response_invalid` / `input_market_value_invalid` | 応答の形・値の誤り | 続けば相談（`check-source` で事実を見る） |
| `input_market_rows_missing` / `input_calendar_data_mismatch` | 取得先の欠け・表の誤り | 続けば相談。固定済みの値で埋める操作はまだ無い |
| `input_ledger_*` | 台帳の誤り | 台帳を直す（§2）。見出し、列の数、時刻の `+09:00` を見る |
| `input_calendar_not_covered` | 休場日の表の終わりが近い | 表の延長（§8） |
| `session_context_mismatch` | 臨時の休場・短縮の後 | 保守の操作。相談する |
| `publication_stale` | 同時に走った別の実行に負けた | 次の定時の実行が拾う。続けば相談 |

## 8. 休場日の表

- 毎年 12 月に、取引所（ICE）の発表を読んで翌々年の分を足し、**照合の出典と日付を残す**。
- 臨時の休場・短縮取引は、発表されたらその日の前に表を直す。
- 表を直したコードの版を、非公開リポジトリの workflow の `V2_CODE_SHA` に上げる（§9）。
- 表の終わりの 14 日前から、`input_calendar_not_covered` の「判定なし」が毎朝届く。ここに来る前に気づける。

## 9. 版の更新

- 公開リポジトリで受領した版のコミット SHA（40 桁）を、非公開リポジトリの workflow の `V2_CODE_SHA` に書くコミット。そのコミットが版の採用の記録になる。
- `actions/checkout` もタグではなく 40 桁の SHA で固定する（E-2 の時点で公式のリリースの SHA を確かめて書く）。

## 10. 保守の操作

- gitの保存先で、履歴の復元・診断・採用が要るとき：`history.json` をローカルの保存先へ取り出して操作し、公開として戻す。**Claude と一緒に行う**。コードは作らない。
- 手で `v2-*` の参照を書き換えない。

## 11. 巻戻しの確認（ブランチ保護が使えない場合）

- 個人の無料のプランの非公開リポジトリでは、保護ブランチは使えない。ルールセットが使えるかは E-1 で確かめる。
- 使えない場合、正しい古い先頭への巻戻しは hash 鎖では見つからない。影響は同じ日の重複の通知で、誤った判定ではない。推奨は、このリスクを受け入れることで、Rocky さんの判断として記録する。
- 実行の記録の `history_digest`（12 桁）が、前の朝から続いているかを時々見る。

## 12. 開始の境界

- **E-2 の `init --mode dry` の境界は、`init` の時点で閉じた最後のセッション。台帳は、その次のセッションから毎日記録する。**
- **E-4 の本番の `init` の境界は、試運転と同じ日**にする。そうすると、最初の本番の朝が台帳を再生して、試運転と同じ状態（armed・連続数）から始まる。直近のセッションを境界にすると、armed が「不明」に戻る。
- 台帳は E-2 から E-5 まで毎日続けて記録する。

## 13. 取得の失敗の理由

実行の記録の `fetch_failure: <記号> <語>` の語の読み方：

| 語 | 意味 | 扱い |
|---|---|---|
| `http_429` | 回数の制限・拒否 | 取得先を考え直す材料。続けば相談 |
| `http_5xx`（`http_500`・`http_503` 等） | 取得先の不調 | 次の朝を待つ。続けば相談 |
| `http_4xx`（429 以外） | 取得先に拒まれた | 続けば相談 |
| `timeout` | 時間切れ（30 秒） | 取得先の不調。続けば相談 |
| `url_error` | 名前の解決の失敗・接続の拒否 | ネットワーク・取得先の不調。続けば相談 |
| `size` | 応答が 8 MB を超えた | 相談 |
| `other` | ほかの失敗 | 相談 |

URL・応答の本文・例外の文面は記録に出ない。再試行はしない（代わりに 1 朝 2 回走らせる）。

## 段階ごとの手順と確かめること

### E-1 非公開リポジトリ（Rocky さんの操作。作成の直前に承認）

- 非公開リポジトリを作成する（このセッションからは作れない）。
- 確かめる：ブランチ保護・ルールセットが使えるか（§11）、Actions の無料の枠（1 朝 2 回 × 約 1 分。月に数十分〜百数十分の見込み）。課金が要るなら止めて知らせる。
- 結果を記録する。

### E-2 workflow の追加（送信なし。追加の直前に承認）

- ひな形（`docs/ops/V2_MORNING_WORKFLOW_TEMPLATE.yml`）を非公開リポジトリの `.github/workflows/v2-morning.yml` に写す。`V2_MODE: dry`、秘密なし。cron の行を含むコミットは Rocky さん本人が行い、失敗のメールを受け取る設定にする（§1）。
- 確かめる：
  - `actions/checkout` の公式のリリースの SHA を書いたか。
  - `queue: max` を GitHub が受け付けたか（受け付けなければ、読むだけのコマンドを別のグループにする形だけで進め、「待ちの実行があるときは手動の実行をしない」）。
  - `init --mode dry` の最初の push が通ったか（checkout の資格情報で `v2-*` の参照へ push できるか。使った `actions/checkout` の SHA と浅いクローンかどうかを記録）。
  - `v2-ledger` の最初のコミット（見出しの 1 行だけ。§2）。

### E-3 送信なしの試運転（開始の直前に承認）

- 最初に、定時の実行より前に `check-source` を手動で 1 回走らせ、取得が通るかを確かめる。続けて拒否されたときに何回で止めて相談するかは、開始の承認のときに決める。
- 定時の実行（1 朝 2 回）を 10 セッション以上。`check-source` の点検（毎朝の 2 回目の後に手動、または 3 回目の定時）。文面を Rocky さんが読む。
- 合否の基準（12 項目。基準の数は案で、試運転の前に変えてよい）：
  1. 連続した 10 セッション以上。月曜のセッション（日本時間の火曜の朝）を含む。できれば休場日の翌日と、IEF の分配落ち（毎月初め）の日。
  2. 各朝の 2 回の実行の取得の成否と理由（`fetch_failure` の語）。**同じ朝の 2 回とも失敗する朝が無いこと**、10 セッションで 1 回目の失敗が 2 回以下。
  3. 応答の形：`meta.symbol` が合う、時刻（ニューヨーク）が一定（寄付き 9:30 等）、`adjclose` がある、引けの後に対象日の行が 1 つ（2 つ返る形が無いこと）。
  4. 表の日の欠け：2026-01-02 以後の表の日で、行が無い・`null` の日が 4 記号とも 0。
  5. 2026 年より前：研究のデータと比べた日付の差（応答だけ・研究だけ）。SOXX で研究だけにある日が 0。
  6. 研究との値の差：調整後終値の日次の騰落率の差の最大と、1e-4 を超える日の数。
  7. 確定前の値の固定：翌朝の `check-source` で `pin_last_close_changed` が全朝で false。
  8. 書込みと資格情報：4 つの参照への push が通る。git の版と Python の版を記録。
  9. 時間：各朝の `seconds.load_inputs`・`seconds.morning_job`・`seconds.outbox_load` と `outbox_files`。閾値は `morning_job` が 60 秒超か `outbox_files` が 1,500 超。
  10. 文面と F&G の記録：判定あり・判定なしの文面を読み、送ってよい形かを決める。F&G の記録が 1 回目に間に合わなかった朝の数。
  11. 定時の遅れ：各実行の予定時刻と開始時刻の差。2 回とも 1 時間以上遅れた朝が無いこと。
  12. 失敗のメール：終了コード 1 の定時の実行があった場合、失敗のメールが届いたか。
- 終わりに合否を記録し、E-4 へ進むかを Rocky さんが決める。

### E-4 実送信の試験（登録と送信の直前に承認）

- Discord で新しい Webhook を作り、非公開リポジトリの秘密 `V2_DISCORD_WEBHOOK_URL` に登録する（Rocky さんの操作。**値は Claude に見せない**。Webhook の画面の URL をそのまま登録する。`?` を含む URL は送られない）。
- 手動の実行の入力 `mode` で `live` を選び（定時の実行は `V2_MODE: dry` のまま）、`init`（境界は試運転と同じ日。§12）の後、`morning` を 1 回。
- 確かめる：届いた文面の見出しが「【詳細】」で、メンションが起きていない（`@everyone` 等）。

### E-5 本番の定時実行（有効化の直前に承認）

- workflow の `V2_MODE` を `live` にするコミット（これが本番の開始の記録）。公開リポジトリの main のジョブは停止のまま。
- 「完成」は、E-5 の後に、本番の朝が続けて届くことで確かめる。

## 付録：この手順書で使う語

- 対象日 D：その朝の時点で閉じた最後の米国の取引日。
- 鍵：`<D>-morning`（判定あり）・`<D>-halt`（判定なし）・`<日付>-error`（実行の誤り）。
- `dry`：送信なしの試運転（`v2-dry-*` の参照）。`live`：本番（`v2-state`・`v2-outbox`・`v2-market`）。台帳 `v2-ledger` は両方で同じ。
