## 1. 最終目標と、この計画の位置づけ

既存ツールの「通知が動かない」不具合を解消し、検証から選んだアラート基準を実装したVer.2を完成させる。米国市場の確定データを基に、日本時間の朝に状況と売買候補を確認でき、ユーザーがF&Gの現在値を目視して、楽天証券で手動発注する運用を支援する。

戦略の評価目的は、損切りを行わず、税引後利益を全額再投資した場合の最終総資産の最大化である。最大ドローダウンは順位を決める制約・減点項目にしない。自動売買への拡張は今回の範囲に含めない。

本計画の作成に伴うGitHubコード・Actions設定・Discord通知先の変更は行わない。現行リポジトリのURL、対象コミット、現在の実行ログ、故障の根本原因は、次の工程で確認する。

## 4. 全体工程

不具合の原因調査と戦略の残検証は並行して進める。通知経路の修正は単独で検証できる形にし、最終的な売買基準と混ぜて原因を追いにくくしない。

| 工程 | 作業と成果物 | Claudeの主なレビュー | 完了条件・依存関係 |
|---|---|---|---|
| 0 現状固定・不具合再現 | 対象コミット、構成図、実行経路、再現手順、故障原因と修正案 | 原因と証拠が対応しているか。現行機能の見落としがないか | 何が・どこで・なぜ動かないかを再現可能に説明。最優先で開始 |
| 1 検証の収束 | 売却しない／全売却／部分利確の比較、候補表、採否理由、未解決データ一覧 | 最終総資産という目的と整合するか。先読み・探索の偏りがないか | 実装する候補と保留事項を明示。工程0と並行可能 |
| 2 売買・通知仕様の確定 | 指標・状態・資金・手動入力・通知文・執行条件の仕様書 | 研究と実運用の食い違い、損切り禁止と注文方法の整合 | 分岐・境界値・欠損時の動作を具体例で説明可能。工程1を反映 |

| 4 V2基準の実装 | 確定仕様に基づく判定・状態保存・通知、設定、運用手順 | 仕様との一致、約定前の状態更新、データ時刻・再実行の扱い | 仕様の各条件をコードとテストへ対応付け。工程2・3を統合 |

## 5. 工程0：最初に確認する不具合

現行コードを読み、実際のログと対応させて調査する。F&G取得の失敗やスケジュールの問題など、候補を原因と決めつけない。

1. 対象リポジトリURL、既定ブランチ、コミットSHA、関連ファイル、最後に正常動作した版を固定する。
2. 「Actionsが起動しない」「起動するが途中で落ちる」「判定まで通るが通知されない」「正常に条件不成立」のどこに該当するかを切り分ける。
3. 実行スケジュール、タイムゾーン、実行権限、依存関係、データ取得先、Discord送信、必要ならSheets等の保存先まで追う。
4. 認証設定は必要な変数名と設定有無を確認する。秘密値をレポートやログに出さない。
5. 本番へ送信しない模擬実行で、障害を再現する。既存通知の抑制・重複防止条件も確認する。
6. 原因ごとに「証拠／影響／修正差分案／確認方法」を整理する。

成果物は、現状診断書と具体的な修正案。GitHubや既存通知設定へ反映する前に差分を提示する。Claudeには、再現手順・該当コード・秘匿化したログを同じ版で渡す。

## 6. 工程1：追加検証を収束させる

追加検証は、次の順に限定する。結果を見て際限なくパラメーターを増やさない。

### 必須の比較

- 同一条件で「売却しない」「既存の全売却基準」「部分利確」を比較する。基準候補は初回あり＋25%、売却条件は利益20%またはRSI75を出発点とする。
- 部分利確は、売却条件到達時に保有株の25・50・75%を残す少数の候補を提案する。端数処理、残した株の原価、追加購入、次回利確の再判定・再通知を先に定義する。毎日同じ条件で売り続ける仕様を暗黙に入れない。
- 主評価は最終時価総資産とし、実現税引後利益・未実現損益・待機資金・分配金・売買回数を分解する。最終日に仮想清算した税引後資産も補助指標として併記し、目的関数を途中で変更しない。
- 2024年10月、2025年1・4・7・10月、2026年1月の独立開始を共通終了日で比較する。途中までの資産を持ち込まない。開始日が違っても市場期間は重なるため、独立した市場標本と呼ばない。
- 入力・コード・設定・台帳を固定し、過去の結果に対する差を説明する。既に調整に使った期間を未使用の検証期間と扱わない。

初回配分と再エントリー配分の分離、20%近傍の細かな利確率探索は、上記で採否が決まらない場合の追加枠とする。現在の研究エンジンの実行可能性の限界を明記して比較し、工程2で決まった執行モデルを反映した後に最終確認する。

### 日足運用と分足・NBBOの扱い

2026-10-26の最新方針は、確定日足で候補日を決め、次回開場で手動購入する運用。日足バックテストは次回Openを代理約定価格として使い、実約定と区別する。分足・NBBOの未取得を日足ルール比較の停止理由にしない。

直後/1/3/5分の最適化は当面対象外・未検証として保存。追加API登録・認証・取得・課金は保留し、推定値を分単位の実測結果と呼ばない。

### 損切り禁止と売却注文

これまでの研究には「翌寄付きの実価格を見て、税引前の費用控除後利益が2%以上なら売る」という判定がある。これは、寄付き前に出す成行売りの実行仕様にはそのまま移せない。研究上の2%ゲートと、損失売却を防ぐ最低条件も別に定義する。

候補通知に最低許容売却価格を添え、発注直前にユーザーが確認する方法や、売却下限を設定した指値などを比較して決める。指値を採用する場合も、約定せず保有を続ける場合、部分約定、注文期限、費用を明記する。注文方法は本計画では決定しない。無条件の成行売りで「損切り禁止を保証」と表示する仕様は採用しない。

### F&Gの目視と毎朝の運用

技術条件だけではExFearの発生を捕捉できないため、技術アラートがない日もF&Gの目視確認を促す。未入力のF&Gを過去の履歴値で埋めて、現在の購入条件が確定したと通知しない。

GitHubの定期実行中に人の入力を待つ仕組みを前提にせず、「朝の技術情報・確認項目の通知」と「目視入力後の再判定」を分けて設計する。手動再実行・入力保存など、既存構成で可能な方法を調べてから選ぶ。新しいWebアプリ等を当然の前提にしない。

## 8. 工程3〜5：実装と受入確認

既存構成を確認してから最小限の変更で進める。不具合修正と売買基準変更は、別の差分としてレビューできるようにする。指標・判定の計算と、データ取得・状態保存・通知送信を分離できる範囲で整理し、研究と本番が別の式で動くことを防ぐ。

受入確認は、実際の原因・仕様の境界・運用障害に対応するものに絞る。

| 確認対象 | 必須の確認例 |
|---|---|
| 不具合解消 | 工程0と同じ条件で故障が再発しない。失敗時はどこで止まったか分かる |
| 条件の境界 | F&Gの25・30、RSI55・75、利益率の境界、通常買いの立上がり、3回連続と途中欠損 |
| 状態遷移 | 初回・保有中・全売却後・部分利確後・ExFear中で条件競合や重複購入候補が起きない |
| 会計 | 整数株、費用込み平均原価、税、残現金、分配金、実約定後の更新。実売却の損失判定も確認 |
| データ・時刻 | 最新終値の未確定・欠損・古い値、休場、夏冬時間、短縮取引。取得失敗を条件不成立と混同しない |
| 通知・復旧 | 同じ取引日の再実行、送信後の途中失敗、送信失敗、再試行、永続状態の読み書き失敗 |
| 手動操作 | F&G未入力／入力済み／古い入力、未約定、部分約定、注文失効。通知と実約定を混同しない |
| 仕様との一致 | 固定入力から期待した候補・理由・参考値が出る。基準変更による過去台帳の差を説明できる |

模擬送信から始め、承認されたテスト先で送信確認する。本番の既存Discordへ試験メッセージを送ることは、このロードマップ作成では承認されていない。

並行確認では、まず発注判断に使わない記録として期待出力と実出力を照合する。定期実行の起動・データ取得・判定・保存・送信結果を一連で確認する。通知先への配信受付と、ユーザーが実際に読んだことは区別する。
