## 4. 特に見てほしいとされた点

### 4.1 新しいパッケージ`v2_git_store`で受領済みパッケージを変えないこと

妥当。理由：

- S4-Bの`morning_job`・`resend`・`outbox_status`は`isinstance(outbox, LocalOutbox)`を見るので、子クラスにすればv2_notifyは無変更で使える（job.py `_check_parts`、`__init__.py` `outbox_status`）。
- `morning_job`は`outbox.status`を例外処理なしで2か所呼ぶ（判定ありの確認と`_take_and_send`の最初）。T-2の「読込みは例外を出さずDAMAGED」はこのために必要で、正しい。DAMAGEDならHALT・ERRORはSKIPPED_JUDGMENT_EXISTS、MORNINGはSKIPPED_CLAIMEDになり、どれも送らない（試行の場面7、X4で確認）。
- S4-Aの`run_morning`は、保存先の`CoreError`をすべてSTOPPEDにし、`store_commit_uncertain`のときだけ`reconcile`を1回呼ぶ（run.py）。設計§5の表は、この受領済みの振る舞いに合わせて既存のコードだけを使っている。`reconcile`の中の取得の失敗もSTOPPEDになる（P-10(a)）。
- 上書きを公開のメソッドに限り、基底の非公開の名前を使わない規則（依頼書§3の9、S4C-16）は、試行の下書き（`_mirror`・`_refresh`は自分の属性）でも守れることを確かめた。

### 4.2 §9.1 S4-BのEND＝6cab050の固定

妥当。tests/v2_notify/test_s4b_09_scope.pyの18行目が`END = None`であることを6cab050で確かめた。S4-A→S4-Bのときと同じ形（7行目のSTARTは6ad609f、18行目だけを替える）。試行の木で、ENDの固定と仮の範囲試験を入れた状態の範囲の鎖34件・test_s4b_09は合格し、仮の範囲試験を外す（ENDだけ固定）と`test_sc_02_chain`の2件（開いた範囲が最後でない／開いた範囲が2つ）が失敗した。受領記録983ced8の注記どおりである。

### 4.3 §9.2 P-01〜P-04の行き先

おおむね妥当。

- P-01（予備の鍵のERROR）をS4-Eの最初の実装単位へ：予備の鍵に落ちるのはsessionsが壊れたときだけで、sessionsを作るのはS4-Dなので、S4-Dの後に直す理由は筋が通る。誤りの向きも「判定の後に誤りの通知」で、無通知・誤判定ではない。
- P-02・P-03をS4-Eの手順へ：妥当。gitの保存先では途中まで書いた意図がリモートに残らない（pushは基底の作成が成功した後だけ）という設計§6の説明は、試行のコードと合っている。ただし、gitの保存先では「リモートに届かない一時的な失敗」でもDAMAGEDと読まれ、再送がREFUSED_DAMAGEDになる（P-03）ので、手順にその区別を書く必要がある。
- P-04：P-01と同じ単位に入れると明記するとよい（P-08）。
- R2-P02を次にtest_s4b_06・結果文書を触る機会に：採否9b4d786のとおり。

### 4.4 §9.3 R2-P01（S4-Eの入口でdurabilityを1か所で決める）の引き継ぎ

妥当。採否9b4d786の文（入口でdurabilityを1か所で決め、送信・状態確認に同じ値を渡す）をそのまま条件にし、GitOutboxについて「写しは`file_sync_only`に固定なので、durabilityの選択は無い。同じ種類・同じ参照のoutboxを渡すことを確かめる」と補うのは、内容を変えずに適用範囲を広げたもので、採否を変えていない。写しを`file_sync_only`に固定する理由（正本はリモートのコミット、写しは毎回作り直す）も正しい。`file_sync_only`は構築時にディレクトリの同期を試さないので、Windowsでも作れる。

### 4.5 §8 巻戻しの表示をS4-Cでは入れない推奨

賛成する。表示を入れるにはS4-AのRunReportとS4-Bのcomposeを変える必要があり、D-1（受領済みを変えない）と両立しない。巻戻しで起きるのは、outboxも巻き戻された場合の同じDの重複の通知で、判定の誤りではない、という評価も、台帳と市場データが同じなら正しい（改訂がある場合の残りのリスクはP-10(b)）。S4-Eで保護の可否を確かめてから決める順序がよい。ただし、保護規則を入れると`[remote rejected]`が実際に起き得るので、N-02の分類をS4-Cで先に直しておくことが、この推奨の前提になる。

### 4.6 同時実行（判定あり1通＋判定なし1通、二重APPLY 0回）

再現した。2×10・3×10・4×10のすべてで送信は判定あり1通と判定なし1通、二重のAPPLYは0回、3・4並行の残りの実行は判定なしをSKIPPED_CLAIMEDにした。S4-BのT-3と同じ結果で、本番はActionsのconcurrencyで1実行にする（採用済みD-2）扱いのままでよい。

- 判定なしの文面に「同時の実行」の注記が付くのは、拒否を既存の`publication_stale`にしたため（T-3）で、正しい。ただし、`[remote rejected]`まで同じにするのは避ける（N-02）。
- 同じ秒に同じ候補を保存する場合は、両方がPUBLISHEDになり、判定なしは出ない（P-02）。結果は安全側だが、受入の書き方を合わせる。
- 二重のAPPLYが起きないのは、どのpushも早送りだけで、各公開がC-2の`check_publication`を取得した今のバイトに対して通るためである。outboxの「二重に送らない」は、N-01を直せば、写しではなくリモートのコミットで保証される。
