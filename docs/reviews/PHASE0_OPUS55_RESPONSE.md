## 1. R-01：重大指摘を受けて仕様案を修正

毎回の実行結果通知を必要な要件として、推奨案へ追加する。正常な条件未達でも「対象日・データ検査結果・判定完了・条件未達」を明示する。売買候補がある場合も、確認済み／未確認条件を分け、完了と売買の実行を混同しない。

| 状態 | 表示と動作の案 |
|---|---|
| 正常・条件未達 | 完了サマリを通知。通常の無通知をなくす |
| 正常・候補あり | 検査済み対象日と候補、目視F&G等の未確認事項を通知。実約定扱いにしない |
| データ・計算・保存異常 | 売買判定を止め、運用エラー／部分失敗と理由を通知。正常な条件未達にしない |
| pip等のステップ失敗 | アプリ本体と分離した完了報告処理で失敗を通知する案。報告処理自体に同じpip依存を持たせない |
| ワークフロー未起動・報告経路故障 | 完了通知なし＝未確認。内部の完了報告だけで自動検知・通知できるとはしない |

起動済みワークフローの報告は、先行ジョブの失敗時も実行する独立した後処理を検討する。ただしワークフロー自体の未起動、実行基盤全体の停止、同じWebhookの故障はこれだけで解決しない。

対象セッションと日本時間の確認期限を決め、「届かない場合は正常とみなさない」という運用を定義する。自動の未起動検知まで求める場合は独立した監視が必要で、別の採否・権限・費用の判断とする。監視やGitHub失敗通知を未設定のまま整備済みとしない。確認期限は§5とユーザーの運用を確認してから決める。

回数制限、配信不明の扱い、重複防止は維持する。完了通知の再送だけで売買候補を再生成したり、保有状態を更新しない。通知の受付・作成応答と、利用者の読了は区別する。

## 2. R-02：不十分だった証拠の解釈を補足

完全データ扱いの#138・139・143でも旧全額売却案内の送信処理へ到達したことを、既存JSONとコードから確認した。前回の追加調査には該当ログ・送信表示を保存していたが、これを「原価未確認の売却案内3回」として明示していなかった点を補った。

欠損時の8回とは別の3回。今回の19定期実行の証拠範囲で、売りPOST到達は合計11回（欠損8＋有限値3）。いずれも実配信・約定は未確認。「有限値」は独立した価格照合や生データ全体の完全性の保証でもない。

原価・保有・費用・執行条件を確認できない間は売却推奨を出さない案を維持する。Opus側の整合所見はユーザーの採用承認とは区別する。データ検査だけ修正して旧全額売却案内を復帰させる提案はしない。

## 3. ユーザーが決める現行運用

推奨は **修正・確認まで現行ワークフローを一時停止**。価格欠損だけでなく有限値の日も原価を見ず売却を案内するため、停止の方が誤って利用する余地を抑えられる。

| 選択肢 | 影響 |
|---|---|
| 一時停止（推奨） | 定期の買い／売り通知とシート追記も止まる。手動再実行もしない。既存保有や証券口座を操作するものではない |
| 継続し、現行売り通知を無効扱い | 利用者が毎回区別する必要がある。欠損による無通知や古い指標・原価未検査は解消しない |

対象は `SOXL Daily Update`、ワークフローファイル `.github/workflows/schedule.yml`、workflow ID `261792748`。main先端は10/26確認時も7731ef0のまま。最新の観測は#152（10/24日本時間08:56）で、有限値・買い予備通知へのPOST到達を記録。現在の有効／無効フラグは取得機能の制約で未確認。停止済みとは扱わない。

停止は実運用の変更のため、従来の「既存設定は承認なしで変更しない」というユーザー指示に従い、明示承認後に行う。現在は承認待ち。停止中のF&G目視確認など、ユーザーの手動確認をこのコードへ依存させない。
