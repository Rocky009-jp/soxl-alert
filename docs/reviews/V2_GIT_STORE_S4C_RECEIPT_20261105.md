## 4. S4-Eへの申し送り

1. **同時実行グループ**：v2-state・v2-outboxを書く実行（定時の朝の実行2回、手動の再送）を、Actionsの1つの`concurrency`グループに並べる（取り消さず待たせる）。これで、別idの再送のCLAIM_FAILEDや朝の処理の競合は本番では起きず、今のコードの競合の処理は後ろ盾として残る。
2. **資格情報の渡し方**：`Git`は親の環境の`GIT_`で始まる変数をすべて除く（`GIT_SSH_COMMAND`・`GIT_ASKPASS`・`GIT_CONFIG_COUNT`等は届かない）。別の非公開リポジトリへの資格情報は、作業場所のリポジトリのgit設定（例：`core.sshCommand`でデプロイキー、`http.<url>.extraheader`）で渡し、`Git`の環境の規則は変えない。actions/checkoutのextraheaderはチェックアウトしたリポジトリ用で、別の非公開リポジトリには使えない。ランタイムが利用者の全体設定（`~/.gitconfig`）を読むことは、S4-Eの判断として結果・手順に書く（設計レビューP-06）。
3. **outboxの大きさ**：S4-Eの受入に、outboxのファイル数と読込みの時間を1行入れ、ActionsとWindowsで測る。遅ければ`git cat-file --batch`でまとめるか、古いファイルを別の参照へ移す運用を設計する。
4. **利用者向けの手順**：手動の再送がCLAIM_FAILEDなら、`outbox_status`を見てから同じidでもう一度依頼する（CLAIM_FAILEDの再送はリモートに何も残さない）。

前の段階からの申し送り（設計§9.2のS4-B P-01〜P-04、R2-P01、設計§8の巻戻しの表示、§11の条件、設計レビューP-02〜P-10）は、設計第2版に書かれたとおりで変わらない。
